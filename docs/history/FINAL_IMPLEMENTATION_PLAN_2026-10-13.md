## 확정한 기준과 남은 범위

감사 당시 프로젝트 소유 파일 186개, 단위 검사 135개, 격리 Electron 검사 14종의 결과는 [완료 근거](../../artifacts/final-review-2026-10-13/completion-audit.json)에 있다. 계획 작성 전 186개 파일의 현재 해시가 감사 ledger와 모두 일치함을 확인했다. 아래 표는 새 구현과 검증의 계획이며, 기존 검사 결과를 새 후보나 다른 OS의 통과 결과로 사용하지 않는다.

## 공통 구현 규칙

단순 조건, 문자열, 반복, 작은 인덱스는 사용하는 함수 안에 둔다. 함수 길이나 줄 수만으로 helper를 만들지 않는다. 프로세스 연결, 저장, 캐릭터 팩처럼 소유권과 검증 경계가 다른 책임만 모듈로 나눈다. 기존 CommonJS 메인·ESM 렌더러·좁은 preload IPC 구조와 의존성 고정을 따른다.

질문은 접수 순서대로 확정하고 동시에 한 턴만 실행한다. 승인·추가 질문의 답변과 중단은 질문 FIFO에 넣지 않는다. 복구·재시작·절전 해제에서 미완료 질문을 자동 재전송하지 않는다. 질문 접수 시 고정한 모델·말투·목적·첨부 사본을 실행까지 유지한다.

캐릭터 팩은 검증한 데이터와 자산만 포함한다. 임의 코드, 외부 실행 플러그인, 팩 오디오 실행 구조를 추가하지 않는다. Markdown 정제와 외부 링크 정책, IPC 호출 창·프레임 검사, 실제/체험 응답 구분을 유지한다. 일반 초안과 큐 편집 초안을 섞지 않는다.

주석은 접수 순서, 파일 소유권, 오래된 응답 배제 등 코드만으로 설명하기 어려운 이유에 한정한다. 수행 내용을 그대로 반복하는 주석이나 완료된 TODO는 추가하지 않는다. 역사 문서·실패 기록·복구 근거는 현재 결과와 구분해 보존한다.

## 0. 작업 기준 보존

1. `git status`와 수정 파일 목록을 저장하고 기존 변경을 포함한 작업 시작 사본·SHA-256을 남긴다. Git checkout/reset을 되돌림 수단으로 사용하지 않는다.
2. 소스·생성 번들·고지·lockfile·앱 metadata와 일반/staging/rollback 앱의 실제 경로를 대조한다. 프로필과 CLI 인증 저장소는 원본 위치를 기록하되 인증 내용은 로그나 결과물에 넣지 않는다.
3. 제품 변경 전 `npm run lint`, `npm run check`, `npm test`를 실행한다. 실행 코드가 변경되면 해당 Electron 경로를 우선 검사하고 전달 전 14종 전체를 실행한다.
4. 결과 폴더를 실행별로 분리하고 소스·스크립트·fixture 해시, 환경, exitCode, 실패 로그를 저장한다. 이전 감사 폴더의 JSON을 새 실행 결과로 덮어쓰지 않는다.

완료 조건은 시작 사본으로 기존 수정 상태를 복원할 수 있고, 현재 검사 실패와 새 변경의 실패를 구분할 수 있는 것이다. 의존성 재설치나 자산 재생성은 기존 파일이 유효하면 수행하지 않는다.

## 1. 최신 수정의 패키지 후보

대상은 [package.json](../../package.json), [package-lock.json](../../package-lock.json), [패키징](../../scripts/package.cjs), [패키지 검사](../../scripts/verify-package.cjs), [빌드 안내](../BUILD_GUIDE.md)다. `package.cjs`의 `buildVersion`은 현재 `34`로 고정돼 있어 후보 식별값 변경이 필요하다. 버전만 바꾸는 단계에 새 버전 관리 모듈을 도입하지 않는다.

1. build34와 build33을 서로 다른 보존 경로에 복사하고 ASAR·unpacked worker·plist·아이콘 해시와 서명을 확인한다. 복구본 읽기와 원본 대조가 실패하면 패키징을 시작하지 않는다. 일반 build30과 사용자 프로필을 보존한다.
2. 후보 버전과 빌드 번호를 확정해 package/lock의 프로젝트 버전과 패키징 metadata를 함께 수정한다. Electron 앱 버전 `0.1.0`과 프로젝트 alpha 버전의 차이는 현재 규칙을 따른다.
3. 현재 명령 `npm run package -- --staging`으로 생성한다. 오프라인 캐시가 필요하면 지원하는 `--electron-zip-dir <폴더>`만 사용한다. OS/CPU와 Electron 버전이 맞는 ZIP이 없으면 실패를 기록한다. 현재 스크립트는 `--platform`/`--arch`를 지원하지 않는다.
4. `npm run verify:package -- --archive <새 후보의 app.asar 절대 경로>`를 새 `ONGGI_SMOKE_ROOT`에서 실행한다. 소스와 ASAR의 바이트, 포함 파일 집합, unpacked Store/worker, 프로젝트 버전, 아이콘, 큰 이미지 원본/미리보기와 첨부 사본·저장 복원을 대조한다.
5. macOS plist의 `CFBundleVersion`, 프로젝트 버전, 로컬 ad-hoc 서명과 후보 경로를 별도로 확인한다. 기존 `verify-package.cjs`는 이 모든 OS metadata와 서명, 실제 앱 시작을 자동 검증하지 않는다.
6. 패키지 검사의 격리 프로필과 실제 `.app` 실행을 구분한다. `packaged-resource-smoke.cjs`는 개발 Electron 호스트에서 ASAR의 실제 메인을 로드하는 측정이며, 서명한 네이티브 실행 파일과 모든 FIFO·연결 경로의 수용을 대신하지 않는다. 기존 `--native-notification-review`는 `ONGGI_NATIVE_NOTICE_REVIEW=1`과 절대 경로 `ONGGI_SMOKE_ROOT`를 함께 요구하고 실제 패키지 앱에도 격리 프로필·체험 모드를 적용한다. 이 경로로 네이티브 시작·알림·정상 종료를 확인하고, 실제 새 인증 수용은 별도 OS 테스트 계정 등 분리된 환경에서 확인한다. 개발용 `ONGGI_SMOKE_ROOT`만 설정해 일반 패키지 실행이 격리됐다고 간주하지 않는다.

동일 앱 식별자의 단일 실행 정책 때문에 기존 앱이 열려 있으면 후보 실행이 기존 앱으로 전달될 수 있다. 정상 종료 후 후보 PID·실행 경로·버전을 확인한다. ASAR 불일치, worker 실패, 잘못된 빌드 번호, 종료 실패는 후보 실패다. 실패한 후보와 로그를 보존하고 기존 앱으로 복구한다.

완료 조건은 최신 수정과 후보 바이트가 일치하고 후보의 시작·저장·재열기·정상 종료를 확인하는 것이다. 로컬 후보 생성은 Developer ID/공증·설치 프로그램·외부 배포 완료를 의미하지 않는다. 이후 제품 코드를 바꾸면 이 후보의 통과를 재사용하지 않고 전달할 최종 소스로 다시 생성한다.

## 3. 긴 기록과 자원 계측

대상은 [성능 검사](../../scripts/performance-ui-smoke.cjs), [자원 검사](../../scripts/resource-smoke.cjs), [Store](../../src/store.cjs), [저장 워커](../../src/store-worker.cjs), 메인의 기록 열기·본문 검색·publish 경로다. 먼저 비용을 분리해 측정하고 병목이 확인된 부분만 수정한다.

현재 성능 검사는 1,000개 메시지의 화면 페이지·delta·용량 거절을 검사한다. `ONGGI_PERFORMANCE_DETAIL=1`은 1/8/24MiB 저장·읽기 각 20회, warm sync/open, 이미지 32개 내보내기를 추가 계측한다. 전체 JSON 읽기와 `worker.postMessage` 비용은 남아 있다. 현재 표본이 1/16/30MiB 전체 수용이나 검색·취소 전달 시간의 검증을 의미하지 않는다.

1. 기존 상세 검사를 기준으로 유지하며 1/16/30MiB의 실제 저장 JSON 바이트를 기록하는 표본을 추가한다. 문자열 길이가 아니라 JSON escape·metadata를 포함한 크기로 구성하고 32MiB 계약을 넘지 않게 한다. 100/1,000/10,000개의 짧은 메시지와 소수의 긴 메시지를 구분한다.
2. 저장 직렬화·메인→워커 구조화 복사·워커 쓰기/교체, 로컬 읽기/parse/정제, 기록 열기, 명시적 본문 검색, UI patch 바이트·카드 수를 나누어 측정한다. 원격 기록 페이지 병합은 로컬 JSON 계측과 분리하고 CLI fixture로 먼저 평가한다.
3. 메인/렌더러 heartbeat와 최대 지연, 중단 클릭→메인 수신→모의 CLI interrupt의 전달 시간을 기록한다. CLI의 실제 완료 대기와 혼동하지 않는다. 숨긴 창과 활성 창도 구분한다.
4. 워밍업 뒤 동일 데이터·런타임·전원·창 상태로 반복하고 median/p95·최대치와 오류를 남긴다. 큰 기록은 독립 프로세스 표본도 사용해 이전 GC 영향을 구분한다. 메인·렌더러·워커의 메모리 표본 및 OS peak 지표를 기록하고 샘플링 최고값을 실제 전체 peak로 단정하지 않는다.
5. 지연이 사용자 입력·취소를 막거나 이전 기준보다 반복적으로 악화되는 경로를 우선 수정한다. 기준 수치와 허용 범위는 초기 계측 결과를 보고 먼저 문서에 확정한다. 개선율을 사전에 약속하지 않는다.

| 관측한 병목 | 검토할 최소 변경 | 함께 유지할 조건 |
|---|---|---|
| 동기 전체 읽기/parse가 heartbeat를 막음 | 기존 저장 경계에서 비동기 읽기 또는 워커 정제의 비용 비교 | 바이트 한도, 손상 metadata 정제, 대화/조회 소유권, 원본 보존 |
| 매 저장의 구조화 복사가 지배적 | 기존 워커에 변경 메시지와 필요한 snapshot만 전달하는 방식 검토 | revision·순서·직전 저장 실패·재시작 전체 복원, 불완전 delta 확정 금지 |
| 여러 기록의 본문 검색이 지배적 | 순차 읽기·조회 예산·중간 양보·취소 소유권 검토 | 명시적 검색, 경로 검증, 새 검색의 결과에 이전 검색 결과 혼입 금지 |
| 원격 전체 페이지 병합이 지배적 | 필요한 과거 기록을 조회하는 UI와 cursor 계약을 별도 검토 | 순서·ID 중복·부분 실패·fallback·검증 후 원자적 확정 |

워커 IPC 왕복·복사 비용이 더 크면 이동하지 않는다. DB 도입, 저장 형식 변경, 자동 기록 절삭은 이번 최적화의 기본안이 아니다. 큰 구조 변경이 필요하면 migration과 복구 비용을 포함한 별도 계획으로 범위를 확정한다.

자원 검사는 `ONGGI_RESOURCE_PHASE_MS`로 각 단계 길이를 정하며 Electron 프로세스 CPU 표본이다. CLI 자식 프로세스·배터리·고유 RAM을 측정했다고 표시하지 않는다. 같은 장비/전원/부하의 충분한 표본과 실제 배터리 측정은 C08의 별도 결과로 남긴다.

## 4. 접수·실행·종료 상태의 책임 정리

대상은 메인의 `send`, `runQueue`, `finishJob`, Codex notification/request, `continue-queue`, 큐 편집·취소, `before-quit`과 관련 테스트다. 현재 메인 1,413줄 자체는 결함이 아니다. 분리의 목적은 비동기 작업의 소유자와 정리 순서를 한곳에서 확인하는 것이다.

먼저 다음 소유권과 전이 표를 현재 코드·테스트에 맞춰 확정한다.

| 상태·작업 | 현재 경계와 유지할 계약 |
|---|---|
| 접수 직렬화 | `admissionTail`, `preparing`, `reservedAttachments`. 첫 await 전에 예약하고 실패/취소에서도 해제하며 `queue.length + preparing`의 10개 제한 유지 |
| 실행 큐 | `queue`, `current`, `queuePauses`, `queueEdit`, `queueControlSaving`. 편집 중 선두와 보류 사유를 건너뛰지 않고 한 작업만 소유 |
| 완료 | `job.finishing`, `job.imageWork`, `job.resolve`, timeout. 중복 완료를 합치고 이미지 확정·저장 이후 완료 알림, 해당 job만 해제 |
| CLI 이벤트 | process·thread·turn·job ID. 이전 연결/턴의 이벤트와 늦은 RPC 응답이 새 작업을 변경하지 않음 |
| 저장 | Store의 `saving`, `writeBlocked`, worker·revision. 저장 실패 시 화면과 원본을 보존하고 다음 작업 실행을 보류 |
| 종료·절전 | 앱의 `quitting`, `systemSuspended`, Store/CLI 정리. 신규 접수 금지, 진행 이미지와 저장 수명 정리, 미완료 표시와 재전송 금지 |

1. 이벤트 순서를 바꾸는 기존 계약 검사를 먼저 대조하고 빠진 경계에만 검사를 추가한다. 접수 2개 경합, 모델 조회 중 취소, `turn/start` 응답보다 빠른 완료 알림, 중복 완료, 이미지 저장 지연·실패, 저장 중 종료, interrupt RPC/완료 알림 timeout을 포함한다. 이미 같은 실패를 확인하는 검사는 중복 작성하지 않는다.
2. 상태를 읽는 창·IPC·알림·설정·기록 경로를 함께 표시하고 소유권을 먼저 단일화한다. 같은 mutable 상태를 메인과 새 모듈 양쪽에 두지 않는다.
3. 실제 경계가 성립하면 접수와 실행 수명을 담당하는 모듈 하나를 분리한다. 파일명과 API는 이 표·테스트를 확정한 뒤 정한다. 메인은 Electron 창·IPC 발신자 권한·플랫폼 이벤트를 소유하고 Store/CLI의 기존 책임은 유지한다.
4. 전달 값은 검증한 질문 snapshot과 최소 동작 의존성으로 제한한다. 거대한 `mainContext` 공유, 범용 dispatcher/service container, 필드별 setter/helper를 만들지 않는다. 접수 정책을 모듈로 옮기면 메인에 같은 조건을 중복 유지하지 않는다.
5. 한 책임 이동마다 단위 검사와 attachments/connection-images/timing/delete/stability/lifecycle 회귀를 수행한다. 전달 전 전체 integration과 의존성 순환 검사를 완료한다.

저장 실패·절전·인증·연결 보류가 겹칠 때 하나의 원인 해소가 다른 보류를 지우지 않는지 확인한다. 승인 답변·interrupt가 큐에 막히거나 저장 완료 전에 다음 질문이 실행되면 이동을 되돌린다. 저장 형식과 IPC 계약은 이 단계에서 유지한다.

## 5. 메시지 표시와 검사 계약 정리

대상은 [renderer.mjs](../../src/ui/renderer.mjs)의 큰 `onState`, `messageCache`/`messageCards`, `responseImageObserver`, `acknowledgeRenderedMessages`와 UI 검사다. 현재 901줄에서 메시지 영역의 독립 책임이 성립하는지 먼저 확인한다.

1. message patch 적용, 카드 생성/수정/제거, Markdown 정제, 이미지/첨부 미리보기, 스크롤 앵커, 읽음·시간 ACK의 의존성을 표로 정리한다. 일반/큐 초안, 모델/설정/팩 폼, 질문/승인 UI는 기존 렌더러에 둔다.
2. 메시지 표시 단위가 독립되면 렌더·reset·dispose의 최소 수명을 가진 ESM 모듈 하나로 분리한다. `act`와 최신 상태 접근을 필요한 만큼만 받는다. 상태 복제나 새 전역 이벤트 버스를 만들지 않는다.
3. 제거된 카드의 observer·미리보기 요청·복사 완료 타이머·예약 ACK를 정리한다. 늦은 미리보기 응답은 대화와 카드 소유권이 바뀌면 버린다. 실패 미리보기는 재열기/원본 확인 안내를 유지한다.
4. 미니/전체 전환, 숨김/복원, 이전 기록 추가, 대화 전환, 이미지 단독 응답, pending→ready/failed, 코드 복사 실패를 검사한다. 미노출 카드의 읽음 ACK와 시간 측정 ACK는 목적이 다르므로 기존 조건을 임의로 통합하지 않는다.
5. HTML 비활성 Markdown, DOMPurify 허용 목록, 외부 링크 정책, label/키보드 접근성, 초안과 스크롤 위치를 보존한다. esbuild 번들과 LEGAL 고지를 다시 생성·대조한다.

D05의 문자열 위치 의존 VM 검사는 책임을 옮길 때 해당 경계의 실제 입력/결과 검사로 바꾼다. 모든 VM을 일괄 제거하지 않는다. Electron 실패 주입처럼 유효한 검사는 유지하고 대체 검사가 같은 실패를 잡는지 확인한 뒤 기존 검사를 제거한다.

UI 검사는 RPC 성공 이후 해당 버튼 enabled·첨부 개수·표시 상태를 기한 내 확인한다. 고정 sleep이나 더 긴 timeout으로 통과시키지 않는다. `passed`는 필수 캡처와 정리 이후 확정하고 runner는 결과 JSON과 exitCode를 함께 확인한다. 기능 성공 후 정상 종료가 멈추면 종료 단계·timer/listener·worker·창의 진단을 남기며 강제 종료를 성공으로 계산하지 않는다.

## 6. 보관량 조회와 안전한 정리

대상은 이미지/첨부 저장소, 팩 archive, 말투 MD 백업, 관련 Store 참조와 설정 화면이다. 감사에서 현재 자산·실행 의존성·회귀 fixture의 추가 삭제 근거는 없다. 10월 12일 정리와 복구본은 [기존 정리 결과](LEGACY_FILE_CLEANUP_RESULT_2026-10-12.md)의 보존 정책을 따른다.

1. 먼저 읽기 전용 목록과 용량을 만든다. 모든 소유 대화, 현재 메모리, 초안·예약 첨부, 실행/대기/편집 작업, 내보내기·삭제 저널, 보관 팩·말투에서 참조를 확인한다. 손상되거나 읽지 못한 기록이 있으면 관련 파일을 정리 가능으로 분류하지 않는다.
2. 앱 소유, 참조 중, 미참조 확인, 사용자 수정/출처 불명, 복구 보관을 구분하고 정리 후보·예상 확보량·보존 이유를 표시한다. 해시가 같아도 이미지 원본·preview·첨부·다른 대화의 공유 참조를 모두 확인한다.
3. 첫 결과는 미리보기와 명시적 선택만 제공한다. 자동 만료를 기본 활성화하지 않는다. 팩 archive·MD 백업은 단순 캐시가 아니므로 최근 선택·사용자 변경·복구 역할을 따로 확인한다.
4. 실제 제거 전 후보 경로·파일 식별·바이트 해시·참조를 재검증하고 복구 가능한 격리 보관본과 목록을 만든다. app-owned 루트 밖 경로, symlink, 바뀐 파일, 새 참조는 제외한다. 정리 중 새 저장·내보내기와 충돌하면 삭제 구간을 중단하고 다시 목록을 계산한다.
5. 부분 실패·권한 부족·디스크 부족·취소·종료는 제거/보존 항목과 복구 위치를 정확히 알린다. 복원은 기존 외부 파일을 덮어쓰지 않는다. 선택한 파일만 정리하며 넓은 폴더 recursive 삭제로 대체하지 않는다.

새 정리 모듈은 참조 판정과 제거 수명이 실제 독립 책임일 때만 만든다. 단순 표시·합계 계산을 파일별 helper로 분산하지 않는다. 완료 조건은 다른 대화의 공유 이미지, 사용자 추가/수정 파일, 읽기 실패 기록의 자산, 진행 작업의 첨부를 보존하고 선택 항목만 복구 가능하게 정리하는 것이다.

기존 build31/32 복구 archive, 감사·실패 로그·역사 문서의 파기는 이 기능에 포함하지 않는다. 보존 기간이 필요하면 용량 목록과 대체 복구본의 검증을 바탕으로 별도 확정한다. 원본 미복구인 합성 PNG 두 건의 제한도 기존 결과에 유지한다.

영향 경로만 확인할 때는 `npm run smoke:integration -- attachments connection-images timing stability lifecycle`처럼 현재 runner의 case 이름을 사용한다. 이 목록은 전체 14종을 대신하지 않는다. 계획한 추가 크기·검색·취소 계측은 스크립트에 먼저 구현해야 하며 위 상세 명령을 실행하는 것만으로 완료되지 않는다.

| 변경 | 필요한 검증 | 즉시 중단·되돌림 기준 |
|---|---|---|
| 버전·패키징 | 검사 묶음, source/ASAR/unpacked/metadata/서명, 실제 후보 수명 | 복구본 실패, 바이트 불일치, 다른 앱 실행, worker·종료 실패 |
| 읽기/검색/저장 최적화 | 크기별 전후 계측, 손상 참조·부분 실패·worker 종료·재시작 | 순서/내용 유실, 원본 훼손, 오래된 결과 반영, 입력·취소 악화 |
| 실행 책임 이동 | 경합·중복 완료·승인/중단·큐 편집·절전·종료 회귀 | 동시 턴, FIFO 역전, 자동 재전송, 저장 전 다음 작업 실행 |
| 렌더러 이동 | delta·스크롤·미니/전체·숨김·이미지·접근성·정제·ACK | 잘못된 대화 카드·ACK, 초안 손실, HTML 정책 약화, 관측자 누적 |
| 선택형 정리 | 공유 참조·외부 변경·symlink·실패 복원·실행 중 경합 | 참조 판정 불확실, 사용자 파일 변경/제거, 복구 실패 |

되돌림은 시작 사본에서 해당 단계의 변경만 복원한다. 생성 번들과 고지도 대응하는 소스로 다시 맞춘다. 사용자 데이터 migration을 포함하지 않는 단계에서도 새로 만든 대화/첨부를 옛 프로필로 덮어쓰지 않는다. 실패 후보를 조사 가능한 상태로 남기고 보존한 안정 앱으로 돌아간다.

## 최초 작업 묶음과 최종 완료 조건

다음 실제 작업의 첫 묶음은 **기준 보존 → 현재 검사 → build34/33 복구 확인 → 새 후보 식별·생성·검증 → macOS 핵심 수용과 큰 기록 계측**이다. 메인/렌더러 분리는 그 결과와 계약 검사 이후 진행한다. 성능 변경은 측정한 병목에 한정하고, 보관 정리는 조회·미리보기부터 시작한다.

각 묶음의 결과에는 변경 이유와 대상 파일, 유지한 계약, 직접 실행한 검사, 실패/환경 대기, 복구 위치를 남긴다. TASKS·빌드 가이드·알파 보고는 실제로 완료한 범위만 갱신한다. 마지막 실행 코드 변경 이후의 전체 검사와 패키지 바이트 대조를 통과한 후보에만 해당 결과를 연결한다.

최종 판단은 기능 동작뿐 아니라 정상 종료와 저장 복원, 사용자 원본 보존, FIFO와 중단, 실제/체험 구분까지 포함한다. 로컬 후속 구현 완료와 Windows·새 인증·외부 배포 수용 완료는 각각 판정한다. 이번 계획 작성은 실행 코드 수정·새 패키지 생성·새 모델 호출을 포함하지 않는다.
