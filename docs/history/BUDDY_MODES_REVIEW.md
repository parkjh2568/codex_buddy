# 버디 사용성·스킨·미니 말풍선·페르소나 검토

기준: 2026-10-06, alpha.10 build18. 현재 검증 플랫폼은 macOS Apple Silicon, Electron 44.5.1, Codex CLI 0.160.0이다. Windows 실기 검증과 Slack 구현은 후속 범위다.

## 프로젝트를 시작한 문제와 전제

사용자는 질문할 때마다 큰 앱을 찾아 열기보다, 바탕화면의 친근한 캐릭터에게 즉시 말을 걸고 싶다. 캐릭터를 지켜보는 즐거움과 실용적인 대화가 한 흐름 안에 있어야 한다. 이 접근은 캐릭터의 존재감이 질문 진입 부담을 줄이고, 취향에 맞는 말투가 지속 사용에 도움이 된다는 전제에 서 있다. 이 전제는 장시간 실제 사용으로 평가해야 하며 기능 테스트가 사용자 만족까지 증명하지는 않는다.

기획자로서 먼저 확인할 것은 자주 묻는 질문의 길이, 짧은 답변 후 더 깊은 대화로 넘어가는 빈도, 원치 않는 움직임·말풍선이 방해되는 상황, 원하는 말투의 예시다. 현재 우선순위는 편한 로컬 대화이고, Slack과 여러 클라이언트 FIFO는 사용자의 이전 요청대로 대기한다.

## 구현한 사용 흐름

설정의 **화면과 대화**에서 스킨과 버디를 눌렀을 때의 대화 표시를 선택한다. 기존 프로필의 기본 대화창 설정은 유지한다. 미니 말풍선은 제목 막대·탭·큰 환영 그림을 접고 최근 질문/답변, 입력, 모델/말투 조작만 보여준다. `↗`를 누르면 같은 기록과 입력 초안을 유지한 채 전체 대화 화면으로 펼친다. 설정은 전체 화면에서 조작하고, 다음 캐릭터 클릭이나 단축키 호출에는 선택한 표시 방식을 사용한다.

말풍선은 캐릭터 위쪽을 우선하고 공간이 부족하면 아래쪽에 배치한다. 화면 작업 영역을 벗어나지 않도록 배치하며 꼬리의 가로 위치를 캐릭터에 맞춘다. 기본 크기는 360×410, 전체 대화는 460×740이다. 캐릭터 이동·위치 초기화에 맞춰 열린 미니 말풍선을 이동시키며, 이 배치 갱신은 입력 포커스를 새로 요청하지 않는다. 초기 미니 구현은 답변 중 전송을 제한했다. alpha.14/build29부터 미니에서도 입력·첨부 질문을 대기열에 추가하고 순서·개별 취소를 표시한다. 승인·추가 입력이 필요하면 전체 화면을 연다.

화면에는 말풍선만 표시하지만, 입력 포커스와 OS 간 호환을 위해 내부적으로는 테두리 없는 투명 Electron 창을 사용한다. OS 창 자체가 없는 구현은 아니다. 캐릭터의 비활성 창과 입력 가능한 말풍선 창을 분리해 두 책임을 유지한다. 구석 타일링 미리보기 문제의 소멸은 이전 E10과 마찬가지로 별도 미검증이다.

## 스킨과 캐릭터의 분리

- `paper`: 종이와 올리브. 기본의 따뜻한 분위기.
- `night`: 고요한 밤. 어두운 바탕과 밝은 글씨.
- `mono`: 흑백 갤러리. 색의 정보량을 줄인 화면.

`skins/*.json`은 정해진 열 가지 색상 토큰만 제공한다. CSS·스크립트·외부 URL을 실행하는 스킨은 허용하지 않는다. 설정에는 `skinId`만 저장하고 실제 색상은 검증된 파일에서 가져온다. 대화·설정·코드·말풍선에 같은 팔레트를 적용하며 캐릭터 SVG 색은 유지한다. 이번 배포는 위 세 스킨을 제공한다. 임의 스킨 가져오기 UI는 없으며 새 스킨을 배포하려면 소스의 스킨 JSON을 추가하고 빌드해야 한다.

## 캐릭터별 Markdown 페르소나

| 캐릭터 | 기본 성격 | 선택할 수 있는 말투 |
|---|---|---|
| 옹기 클립 | 흩어진 생각을 묶고 실용적인 행동을 정리 | 친절, 상냥한 장문, 핵심 단답, 퉁퉁이 |
| 새싹 옹기 | 작은 다음 걸음을 돕고 단계별로 설명 | 친절, 상냥한 장문, 핵심 단답, 퉁퉁이 |

각 캐릭터의 `personas/base.md`와 선택한 모드의 MD를 함께 사용한다. 단답 모드는 이모지·인사·반복 설명을 줄이고, 퉁퉁이는 퉁명스러운 반말을 사용한다. 장문 모드는 이유·예시·단계를 충분히 설명한다. 이 파일들은 말투 지시 데이터이며 실행 코드를 호출하지 않는다.

처음 실행하면 `characters/<id>/personas/`의 다섯 템플릿을 사용자 데이터의 `personas/<id>/`에 복사한다. macOS의 현재 활성 파일 위치는 `~/Library/Application Support/OnggiBot/personas/`이며 Windows에서는 Electron 사용자 데이터 위치를 따른다. 설정의 **MD 폴더** 버튼이 실제 활성 경로를 연다. 소스 템플릿 변경으로 기존 사용자의 편집 파일을 덮어쓰지 않는다.

입력 아래 **말투**에서 즉시 전환할 수 있다. 캐릭터별 선택은 `settings.personaModes`에 따로 저장한다. 설정의 접힌 Markdown 편집을 펼쳐 캐릭터와 기본 성격/모드 파일을 선택하고 저장한다. 외부 편집기로 바꾼 내용도 질문을 보낼 때 다시 읽으며, 편집 화면은 **파일 다시 읽기**로 갱신한다. 파일은 UTF-8·16KiB 이하이고 빈 내용, 잘못된 인코딩, 팩 밖 경로·심볼릭 링크를 거절한다. 손상된 파일 때문에 앱 전체를 종료하지 않고 편집 화면에 오류를 보여주며, 해당 파일을 고쳐 저장할 수 있다.

질문을 보낼 때 지시문을 고정한다. 대기 중에 다른 모드로 바꾸거나 MD를 편집해도 이미 보낸 질문은 바뀌지 않는다. 답변 기록에는 캐릭터·모드·지시문 해시를 남기며 원문 답변은 다시 쓰지 않는다.

## 실제 CLI 적용과 검증에서 찾은 이슈

처음에는 세션 재개 시 지시문을 바꾸는 경로를 시험했지만 이 설치 버전에서 첫 말투가 계속 남았다. 이에 `turn/start.collaborationMode.settings.developer_instructions`로 매 질문의 지시문을 전달하도록 수정했다. CLI가 요구하는 `experimentalApi` 기능 협상을 사용한다. 질문의 `input`에는 사용자 원문만 넣고, 모델·추론·속도 선택과 읽기 전용·승인 정책을 유지한다. 같은 CLI 세션에서 말투를 바꿀 수 있다. [공식 App Server 문서](https://learn.chatgpt.com/docs/app-server)

실제 GPT-5.6-Luna/high에서 두 캐릭터 × 네 모드, 총 여덟 응답을 확인했다. 여덟 응답은 하나의 실행 중인 CLI 프로세스와 같은 대화에서 캐릭터를 바꾸며 생성했다. 단답은 102자·94자이고 이모지가 없었으며, 장문은 513자·545자였다. 퉁퉁이는 반말로 응답했다. 결과는 `artifacts/persona-real-smoke.json`에 원문과 해시·시간을 저장했다. 이 샘플은 전환 동작의 증거이며 모든 질문에서 동일한 길이·어조를 보장하는 평가는 아니다.

실제 미니 UI에서도 Luna/high·단답 모드로 질문 전송과 응답 표시를 확인했다. 해당 샘플의 전체 시간은 약 3.51초다. 미니 UI는 조작 부담을 줄이지만 모델 응답 시간을 자체적으로 단축하지는 않는다. 긴 응답·high 추론의 대기 시간은 별도로 고려해야 한다. `artifacts/real-mini-persona-smoke.json`, `real-response-timing.json`이 근거다.

## 구조·라이브러리를 유지한 이유와 최적화

Electron을 유지하면 두 OS에서 같은 대화·Markdown·설정 UI를 쓸 수 있다. Swift 전용 플로팅 구현으로 옮기면 Windows UI와 저장·연결 경로를 별도로 관리해야 한다. 실제 Windows 실행을 검증한 것은 아니며 플랫폼 전용 옵션 분리는 유지한다.

기존 Codex CLI는 현재 로그인·모델 목록·세션·스트리밍을 재사용한다. 별도 AI SDK나 에이전트 프레임워크를 추가하지 않았다. 장점은 연결 경로가 일관된다는 것이고, 비용은 CLI의 실험 프로토콜 변경을 재검증해야 한다는 점이다. 페르소나는 권한을 자동으로 부여하는 규칙이 아니다.

파일 접근·검증은 `personas.cjs`, 색상 데이터 검증은 `skins.cjs`로 분리했다. 단순 화면 상태·선택 처리는 기존 렌더러에서 인라인으로 유지했다. MD와 이미지 카탈로그는 카탈로그가 바뀔 때만 IPC로 전달하며, 응답 청크마다 큰 MD 목록을 JSON으로 다시 직렬화하지 않도록 수정했다. `pickerSettingsSignature`는 모델 선택의 포커스 보존에 사용한다. 실패한 세션별 지시문 상태는 제거했다. CLI clientInfo 버전도 패키지 메타데이터를 읽게 변경했다. 이미지 재생성 스크립트는 기존 페르소나 연결 정보를 보존한다.

## 2026-10-07 최신 버디·모드 재비교

이번 절은 alpha.10 build25 소스의 추가 분석이다. 위 build18 설명·32개 테스트·당시 미검증 목록은 과거 기록이다. 최신 안정화와 30분 CPU 측정은 [build25 적용 기록](PROJECT_REVIEW.md#build25-재검토-적용-기록)을 따른다. build25 파일은 staging에서 검증했으며 실행 앱 교체/최종 네이티브 확인은 Mac 잠금으로 남아 있다. 이번에는 앱 동작을 바꾸거나 새 라이브러리를 설치하지 않고, 실제 코드·최신 공개 문서·설치된 universal-modder 스킬을 읽어 계획을 갱신했다.

### 현재 목표에 대한 판단

목표는 큰 도구로 이동하지 않고 바탕화면에서 질문하고, 캐릭터가 작게 살아 움직이는 즐거움을 얻는 것이다. 이후 Slack 호출·키워드 알림을 받고 싶다는 요구가 있다. 캐릭터 수·3D 품질·자동 행동의 복잡도가 높을수록 좋은 제품이라는 전제는 성립하지 않는다. 사용자가 반복해서 요청한 작은 크기, 자유로운 위치, 클릭 통과, 짧은 안내, 반듯한 입력 UI가 가치 판단의 기준이다.

새 기능을 평가할 때는 질문 시작까지의 조작 수, 초안/대화 연속성, 실제 내용 확인이 필요한 상태의 발견, 원치 않는 움직임/창 열림/소리 빈도, 가져온 팩의 설치·복구 난이도를 먼저 본다. CPU·배터리 수치는 같은 환경의 비교 검증이 있어야 원인과 향상률을 주장할 수 있다. 기존 30분 측정은 통제된 전후 비교가 아니다.

### 모드의 의미를 분리

기존의 캐릭터·스킨·말투 분리는 유지한다. 입력창 하단의 말투/모델 두 조작은 유지하고, 새 표시 프로필·팩/말투 관리·목적 템플릿은 설정 또는 필요한 때의 팝업에 둔다. 모든 축을 입력창에 새 선택기로 추가하지 않는다. ‘모드’ 하나에 외형·말투·권한·모델을 모두 묶으면 어떤 설정이 바뀌었는지 알기 어렵다.

| 축 | 현재 | 추가 후보·원칙 |
|---|---|---|
| 외형 | SVG/PNG/WebP 팩, 기본 둘, 공통 CSS 움직임 | 정적 팩 유지, 선택적인 프레임 애니메이션. 실제 작업 상태가 우선 |
| 표시 | 미니/전체, 수동 움직임 줄이기, OS reduced-motion CSS | 정숙/일상/생동감의 표시 프로필. 기본 크기 50%와 기존 창 정책 유지 |
| 말투 | 캐릭터별 base + 네 MD 모드, 질문별 고정 | 복제/이름 변경/추가/초기화·미리보기. 캐릭터 전용 모드부터 개선 |
| 목적 | 별도 목적 모드 없음 | 설명·번역·글 다듬기 등 선택형 작업 템플릿. 말투와 독립시키되 UI가 복잡해지면 후순위 |
| 알림 | 자기 질문의 응답/승인/오류 안내 | 우선순위·정숙 시간·cooldown·배지. 사용자 조치 필요 상태는 미니 대신 전체/트레이에서 발견 가능하게 함 |
| 모델·실행 | CLI 카탈로그·Luna/high 기본·Standard/Fast·승인 정책 | 시각/말투 프리셋이 모델·Fast·sandbox·실행 권한을 몰래 변경하지 않음 |
| 기억 | 로컬 기록과 같은 CLI thread 재개, 이름 설정 | 사용자가 명시적으로 저장한 선호/기억부터. 대화 저장=모든 대화의 자동 장기 기억으로 설명하지 않음 |

추천 표시 프로필은 다음과 같다. 프리셋은 변경 항목을 보여주고 사용자가 개별 설정을 조정할 수 있어야 한다.

- **정숙:** 자동 대기 움직임/소리/일상 안내 억제. 사용자 요청 응답·승인 필요는 작은 상태 표시로 발견 가능하게 유지. 모드 자체가 현재 질문을 취소하지 않음.
- **일상:** 현재 작은 흔들림·hover 안내·사용자 질문 완료 표시. 초기 기본값 후보이며 기존 사용자의 설정은 유지.
- **생동감:** 눈 깜빡임·짧은 기지개·커서 주변의 제한된 시선 반응. 자동 이동/소리/선제 모델 질문은 기본값에 넣지 않음.

현재 ‘잠자기’는 `sleeping` 표시를 토글하며 다음 질문 실행 때 해제된다. 질문 실행 중 토글하면 승인/작업 상태보다 잠자는 표시가 우선할 수 있다. 이를 ‘알림 무음’이나 ‘작업 중단’으로 설명해서는 안 된다. 사용자 조치 필요 상태와 쉬기 표현의 우선순위를 정하고 기능 의미를 UI에 맞춘다. 포커스/방해 정책과 상태 정리는 M03/M04로 함께 검증한다.

reverse-engineering/mashup-mods는 소스를 가진 Electron 앱에 필요하지 않다. mod-any-game의 게임 설치/로더/anti-cheat 전체 절차도 적용 대상이 아니다. 특정 게임의 자산을 추출하거나 Desktop Mate DLC/Live2D 모델을 코드의 라이선스만 보고 가져오지 않는다. 팩 이미지/음성/모델 이용 조건은 별개다.

### 권장 최소 애니메이션 팩과 제작 흐름

v1 캐릭터의 단일 SVG/PNG/WebP를 계속 지원한다. v2 후보는 `animations`, 공통 캔버스·피벗, 허용 프레임 영역·duration/loop, `rendering: smooth|pixel`, 제작자/출처/라이선스다. 파일별 실제 픽셀 수와 전체 decoded 예산, 상태별 프레임 개수·최대 fps, atlas 사각형 범위를 제한한다. 이 필드/상한은 제안이며 현재 로더가 지원하지 않는다.

1. 기존 클립·새싹의 출력 크기/투명 영역/말풍선 앵커를 기준으로 규격 확정. 논리 크기와 Retina/Windows raster 해상도 구분.
2. 대기 눈 깜빡임 하나(예: 2–4프레임)만 제작. 모든 프레임을 같은 캔버스와 바닥 피벗으로 정규화. 매 프레임 따로 잘라 피벗이 흔들리게 하지 않음.
3. PNG/WebP atlas 또는 검증된 프레임 목록으로 내보내고 다시 읽어 투명 배경 contact sheet 확인. 생성 원본과 배포 파일은 구분.
4. 평소 8–12fps 정도의 낮은 후보로 시작하고 단일 atlas/CSS steps 등 작은 구현부터 선택. 최종 상한/방식은 기능·CPU 측정 뒤 확정. 프레임마다 IPC/저장/LLM 호출을 하지 않음.
5. 모든 상태 전환·캐릭터 교체·drag·hover·쉬기·reduced-motion·숨김·잠금에서 타이머/소스 정리. 바탕화면 창과 클릭 영역은 정해진 bounds를 유지.
6. Windows 혼합 DPI/네 모서리/Snap과 macOS 잠금/Spaces/화면 연결 변경에서 확인. 실패는 기존 idle로 돌아가고 대화·모델·초안을 유지.

모든 팩에 눈/입 부위를 별도 SVG DOM으로 요구하거나 임의 JS/CSS/표현식을 허용하지 않는다. 처음에는 프레임 재생을 현재 renderCharacter 안에 제한적으로 작성하고, 렌더러 종류가 두 개 이상 실제로 필요할 때만 책임 경계를 분리한다. 제조 파이프라인 스크립트는 재현 가능한 입출력/검증을 제공하면 충분하며 범용 게임 엔진을 만들 필요가 없다.

Live2D/VRM은 사용자가 실제 원하는 외형을 2D 팩으로 못 만드는 경우 별도 후보로 둔다. Cubism SDK와 모델 자산의 조건, WebGL/렌더 자원/패키지 배포/Windows 검증이 추가된다. 특히 자유로운 모델 가져오기는 공식 라이선스의 Expandable Application 항목과 관련할 가능성이 있어 배포 전에 적용 여부를 확인해야 한다. 현재 이 앱의 분류를 법적으로 확정하지 않는다. [Live2D 공식 SDK 배포 조건](https://www.live2d.com/en/sdk/license/)

### G1 — 이미지 경계와 작은 글씨

**수정 위치:** `src/packs.cjs`, `src/main.cjs`의 startup/import 경로, `src/ui/renderer.mjs`의 이미지 오류, `skins/paper.json`, `skins/mono.json`, `test/core.test.cjs`, `test/buddy.test.cjs`, 관련 UI smoke와 `docs/CHARACTER_PACKS.md`.

M01-A는 기존 loadPack 안에서 manifest 객체/크기/일반 파일/내부 경로와 참조 파일을 검증한다. manifest 자체의 symlink/팩 밖 연결도 포함해 경계를 맞춘다. 상대 경로 문자열이 달라도 같은 파일을 가리키면 canonical 파일 기준으로 한 번 검증하고 바이트/픽셀 예산을 계산한다. 수신 파일명/MIME/실제 형식이 일치해야 한다.

PNG는 signature·IHDR·필요한 chunk 구조·폭/높이, WebP는 RIFF/WEBP·VP8/VP8L/VP8X 관련 크기와 chunk 경계를 확인한다. 잘린 버퍼에 readUInt를 먼저 적용하지 않으며 offset/길이·곱셈의 안전한 정수 범위를 검사한다. 이는 전체 코덱을 직접 작성하라는 계획이 아니다. [PNG 규격](https://www.w3.org/TR/png-3/), [WebP 컨테이너 규격](https://developers.google.com/speed/webp/docs/riff_container)

기존 파일당 3MiB/팩 24MiB 제한을 유지하고, raster 한 장 2048×2048 이하·팩 고유 raster 8,388,608pixels 이하를 **초기 검증 후보**로 둔다. 단순 RGBA 계산으로 각각 약 16/32MiB지만 decoder/브라우저/IPC의 총 RAM 한도를 뜻하지 않는다. 정상 v1·고해상도 fixture로 충분한지 검증한 뒤 규격에 확정한다. manifest의 논리 크기와 raster 해상도를 같은 값으로 강제하지 않는다.

M01-B의 첫 작업은 작은 PNG/WebP/SVG decode 호환 probe다. Electron nativeImage 공식 공통 형식은 PNG/JPEG이고 WebP까지 지원한다고 보장하지 않는다. 이를 유일한 판정기로 사용해 기존 WebP를 전부 거절하는 구현은 피한다. [Electron nativeImage](https://www.electronjs.org/docs/latest/api/native-image)

필요하면 네트워크/Node 접근이 없는 숨김 sandbox 검증 renderer에서 bounded 데이터의 decode 성공·natural dimensions를 확인한다. createImageBitmap/Image.decode 경로는 후보이며 macOS/Windows 및 SVG 호환 확인 전 확정하지 않는다. Promise를 시간 초과시키는 것만으로 decode가 중지됐다고 보지 않고, 지연/크래시 시 검증 프로세스를 종료·정리하고 설치를 거절하는 수명을 검증한다. 이 경계는 기존 pack metadata 검증과 구분해 테스트하며 일반 이미지 조작 API를 renderer에 노출하지 않는다. [createImageBitmap](https://developer.mozilla.org/en-US/docs/Web/API/Window/createImageBitmap)

애니메이션 PNG/WebP도 탐지 대상으로 포함한다. 자동 재생 이미지가 CSS 움직임 줄이기만으로 정지한다고 가정하지 않는다. v1 설치물의 호환 영향과 정적 대표 프레임 경로를 probe에서 확인하고, 지원 방식/변환/거절 안내를 정한 뒤 변경한다. 현재 사용자 팩을 조용히 변환하거나 원본을 덮어쓰지 않는다.

설치 미리보기와 실제 복사 사이에 원본이 바뀌는 경우를 처리한다. 검증한 immutable bytes/해시를 staging에 쓰거나 복사된 파일을 재검증하고 snapshot과 대조한다. 실패 시 새 staging만 정리하고 현재 팩은 유지한다. decoder가 응답하기 전에 캐릭터 설정/카탈로그를 바꾸지 않는다.

renderer의 이미지 오류는 ‘현재 소스 실패 → 검증된 idle → 내장 placeholder’ 순서로 한 번씩 복구한다. idle도 손상됐을 때 무한 onerror 반복을 막고, 이미 교체한 캐릭터의 늦은 오류/성공이 현재 이미지를 덮어쓰지 못하게 요청 세대/현재 source를 확인한다. fallback은 창 bounds·thread·모델을 바꾸지 않는다.

M02는 paper/mono의 사용되는 작은 필수 텍스트 쌍을 4.5:1 이상으로 보정한다. 팔레트 계산과 실제 배경/opacity/상태를 함께 확인하며 disabled·장식은 구분한다. body 글꼴이나 전체 여백을 동시에 재설계하지 않는다. `skins.cjs`의 색상 타입 검사와 특정 내장 팔레트 회귀 검사는 유지하고, 모든 향후 색상 조합을 무조건 거절하는 일반 규칙을 먼저 추가하지 않는다. [W3C 일반 텍스트 대비 기준](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

**수용 테스트:** 정상 PNG(투명/일반)·정상 WebP(lossy/lossless)·기본 SVG; 비이미지·signature만 정상인 손상 파일·0/초대형 치수·잘린 chunk·경계 pixel 수·alias 중복·symlink·외부 경로; decode 지연/크래시/취소·실패 뒤 재가져오기·늦은 이미지 오류. 세 스킨의 작은 안내·카드 설명·오류·포커스·125/150% 글씨 확대를 확인한다. 기본 두 캐릭터와 이전 팩 원본·설정/대화 보존을 대조한다.

### G2 — 쉬기·정숙·실제 작업 상태

**수정 위치:** `src/main.cjs`의 characterState/notification/request/powerMonitor/runQueue, `src/store.cjs`의 새 설정 기본값·검증, `src/ui/renderer.mjs`, `src/ui/notice.js`, `src/ui/index.html`·CSS, `test/stability.test.cjs`, `scripts/stability-ui-smoke.cjs`, `scripts/timing-ui-smoke.cjs`.

표현 상태의 소유자는 계속 메인이다. 요청·답변 상태는 바꾸지 않고 렌더러가 받는 라벨/움직임 정책을 파생한다. 기존 팩의 7상태 키를 유지하며 준비/대기/수신 상태 때문에 모든 v1 팩의 새 SVG를 요구하지 않는다.

수동 표시 프로필은 ‘현재 설정 유지(custom)’, 정숙, 일상으로 먼저 시작한다. 생동감의 실제 프레임 동작은 G5 이후 활성화하며 없는 기능을 옵션 설명에 쓰지 않는다. 기존 프로필에 새 필드가 없으면 기존 reducedMotion/스킨/표시 방식을 그대로 유지한다. 설정 action의 허용 필드·Store 기본값/정규화·UI 적용/저장/재시작 검증을 한 변경 묶음으로 처리한다. OS reduced-motion과 사용자의 명시적인 움직임 줄이기는 효과 우선이고 자동 감지가 저장된 선호를 덮어쓰지 않는다.

lock/unlock, battery/AC 이벤트는 macOS/Windows의 Electron 경계를 활용하되 미지원/unknown은 현재 선호 유지로 처리한다. 배터리 자동 절감은 첫 배포에서 선택형이며 앱이 처음 배터리 전환됐다는 이유만으로 사용자 설정을 변경하지 않는다. 환경 플래그는 런타임에 두고 user setting과 구분한다. [Electron powerMonitor](https://www.electronjs.org/docs/latest/api/power-monitor)

정숙에서는 일반 안내·자동 움직임을 줄이고 주의를 요구하는 상태는 배지/캐릭터·트레이에서 발견 가능하게 한다. 클릭하면 필요한 경우 전체 승인 화면을 연다. 기본 일상 프로필의 기존 승인 흐름을 바꾸려면 자기 질문 승인/숨김/단축키 동작을 함께 검증한다. 타 앱 포커스를 무조건 빼앗는 정책은 추가하지 않는다. 모든 작업 실패를 매 publish마다 새 팝업/소리로 반복하지 않는다.

**수용 테스트:** 쉬기 중 승인, 승인 해소, 연결 실패, 취소 RPC timeout, 저장 실패, 늦은/다른 thread·turn 이벤트, 빠른 상태 전환, 잠금 중 응답 수신/렌더 ACK 미발생, unlock 후 정확한 ACK, 절전 동안 새 turn 없음·대기 계속/취소·재시작 중단 표시, 새 설정의 저장 실패 롤백/재시작/이전 설정 호환. Windows의 이벤트·포커스는 모의 결과와 네이티브 결과를 구분한다.

### G3 — 작은 개인화 개선·자산 전송 계약

**수정 위치:** `src/personas.cjs`, `src/packs.cjs`, `src/main.cjs`, `src/ui/renderer.mjs`·설정 HTML, `test/buddy.test.cjs`, buddy/stability/performance smoke. preload는 필요한 좁은 action만 이용하며 원시 파일 경로/임의 파일 read API를 추가하지 않는다.

M05-A는 기존 base/네 말투의 ‘제공된 기본 내용으로 복원’부터 한다. 사용자가 선택한 MD 한 파일만 백업하고 현재 저장 함수의 UTF-8/16KiB/원자 교체 경계로 복원한다. 캐릭터·모델 선택이나 다른 MD를 변경하지 않는다. 질문 중에는 기존 snapshot을 유지하고 다음 질문에 적용한다. 제공 템플릿은 immutable source로 두고 활성 편집 파일과 혼동하지 않는다. 편집 중인 미저장 초안은 discard를 명시적으로 선택한 경우만 바꾼다.

M06-A는 ‘읽기·검증·미리보기 → 사용자가 설치/선택 확정’ 흐름이다. 미리보기 화면은 후보 이름·버전·출처·일반/오류 상태 이미지·MD 포함 여부를 보여준다. 모델 응답이 없는 말투 예문은 예문으로 표시한다. 닫기/취소/검증 실패는 디렉터리/선택/등록부에 영향을 주지 않는다. 후보에 대해 메인이 발급한 token/버전을 사용해 늦은 응답과 변경된 원본을 구분한다. 사용자 프로필의 상태 파일/절대 경로/키를 후보 정보나 내보내기에 담지 않는다.

M07의 새 payload는 다음 계약으로 제한한다.

- 목록: ID·이름·설명·버전·설치 출처와 크기 제한된 썸네일/썸네일 요청 식별자. 전체 상태 이미지와 persona 전문은 매 목록 갱신에 넣지 않음.
- 활성 팩: 정규화된 manifest, 현재 팩의 필요한 assets, pack revision/해시. pet과 panel의 welcome/preview가 사용할 범위를 명시함.
- 후보 미리보기: 메인 소유의 preview token으로 연결된 검증 데이터. 같은 action으로 임의 파일/미등록 디렉터리를 읽게 하지 않음.
- 캐시 키: pack ID만으로 끝내지 않고 실제 콘텐츠 revision/해시를 포함. 사용자 MD 변경만으로 이미지 cache를 전부 버리지 않음.
- 수명: 캐릭터 A→B 전환 중 A의 늦은 응답은 버림. 이미지/썸네일/ObjectURL은 cache 교체·창 종료·크래시/재로드에서 해제. preload 구독을 publish마다 누적하지 않음.

처음은 in-memory active cache와 기존 카탈로그 버전으로 구현하고 HTTP 파일 서버/외부 URL/자유로운 custom protocol을 먼저 도입하지 않는다. 새 팩이 많아졌을 때만 카드 수/캐시 예산을 실제 표본으로 조정한다. 현재 작은 기본 둘의 전송 크기를 심각한 성능 문제라고 표현하지 않는다.

**수용 테스트:** 기본 MD 복원·백업·실패 후 원문 보존·미저장 편집 초안·큐 말투 snapshot; 미리보기 취소/검증 실패/원본 변경/중복 확정; 20개 테스트 팩에서 목록 크기·활성 자산 전송 확인; 같은 ID 다른 revision·빠른 A/B 전환·재로드/화면 종료·미니↔전체·이미지 실패. 질문 스트림마다 대형 자산이 다시 전송되지 않는지 검사한다.

### G4 — 사용자 모드 등록과 팩 수명 관리

**설계 먼저 확정할 사항:** 사용자 모드 등록부의 소유자와 schema, 기본/사용자 모드 ID 경계, 설정 변경·MD/등록부 변경의 실패 순서, 팩 교체 시 사용자 MD 보존·새 템플릿 처리, 읽기 전용/잠금 파일과 중간 종료 복구. 이 조건 없이 현재 PersonaLibrary/save와 import-pack에 버튼만 늘리지 않는다.

M05-B는 기본 모드를 직접 삭제/이름 변경하지 않고 사용자의 복제본부터 만든다. 사용자 ID는 앱이 생성하고 표시 이름은 경로로 사용하지 않는다. 현재 base 예약 및 모드 최대 8개를 초기 총량 기준으로 유지하는 후보를 검증한다. 별도 registry(예: `personas/<캐릭터>/modes.json`)와 `<앱생성 ID>.md`를 두고 모든 read/save/resolve/catalog가 같은 등록부·경로 검증을 사용하도록 한다. 이것은 저장 구조 제안이며 아직 파일을 생성하지 않았다.

복제는 ‘MD 검증·새 파일 → 등록부 교체’를 수행하되 자동으로 활성 모드를 바꾸지 않는 흐름부터 한다. index 실패에서는 해당 작업이 만든 파일만 정리한다. 생성 중 종료로 남은 미등록 파일은 사용자 MD라고 가정해 지우지 않고 소유 작업 journal이 확인한 범위만 복구한다. 활성 사용자 모드를 제거하려면 먼저 유효한 다른 모드를 선택하게 하고, 사용자가 선택한 복구 가능한 보관/제거 흐름으로 처리한다. 진행/대기 질문을 포함한 삭제 정책은 UI/메인에서 동일하게 적용한다.

M06-B의 팩 교체는 ‘동일 디스크 staging 작성·재검증 → 이전 팩 backup → 새 팩 활성화 → 설정/목록 반영 → 완료 표시’로 계획한다. directory rename 한 번이 여러 파일·설정을 전부 원자적으로 교체한다고 설명하지 않는다. Windows에서는 열린 파일/백신 검사/권한 때문에 rename이 실패할 수 있으므로 단계 journal, ownership, 이전/새 해시·버전으로 재시작 복구를 정의한다. 기존 Store save journal만으로 팩 폴더까지 복구된다고 가정하지 않는다.

기존 사용자 MD는 덮어쓰지 않는다. 제공 템플릿 갱신·새 모드 추가·기존 모드 제거가 있을 때 사용자의 활성 선택 유효성을 확인한다. 오류 있는 기존 MD를 그대로 우선 선택해 질문만 실패하게 하지 않고, 수정 안내 또는 유효한 선택으로 확인 가능한 전환을 제공한다. 삭제는 기본 팩 보호, 선택 팩의 대체 준비, 대화/이름/모델 보존, persona 보관과 이미지 팩 제거의 구분을 포함한다. 불필요한 영구 삭제를 기본으로 삼지 않는다.

내보내기는 검증된 manifest·참조 자산·사용자가 고른 MD만 새 목적지에 쓴다. 사용자 데이터 디렉터리를 통째로 압축하지 않는다. 첫 버전은 폴더 입출력을 유지하여 ZIP path traversal/추출 라이브러리·시장/다운로드 검증을 동시에 추가하지 않는다. 제작자/출처/자산 라이선스·호환 버전은 metadata이며 실행 URL이나 권한이 아니다.

복구 로직은 기존 packs/personas 저장 책임 안에 둔다. 작업 규모가 커져 검증/복구 수명 자체가 독립 책임이 된 경우에만 lifecycle 모듈을 분리한다. 문자열 다듬기·단일 필드 설정 등을 별도 helper로 추출하지 않는다.

**수용 테스트:** 새 모드 생성/중복/개수/경로/인코딩·index save 실패·부분 파일·active 모드 제거·재시작; 팩 교체 각 단계 직전/직후 강제 종료·disk full·readonly·Windows locked file·복구 실패 시 write block/원본 유지; 새 버전과 기존 사용자 MD·현재/대기 대화 보존; 삭제 후 재가져오기·폴더 내보내기 재읽기·개인 데이터 비포함.

### G5 — 최소 프레임 팩과 플랫폼 확인

**수정 위치:** `docs/CHARACTER_PACKS.md`의 v2 후보 명세 → `src/packs.cjs`와 `scripts/check.cjs` → renderer/CSS → 기존 캐릭터 생성/검증 스크립트 → main의 크기/포인터 처리·Store 배율 → pack/좌표/UI/자원 테스트 순서다.

처음에는 기존 클립의 눈 깜빡임 한 동작만 만든다. v1 정적 팩은 변경하지 않고 v2의 공통 캔버스·피벗·프레임 사각형·duration/loop·smooth/pixel 필드를 whitelist로 처리한다. atlas/프레임 decoded 예산은 G1 규격을 따른다. 프레임 수·fps 상한과 필드 누락/미지원 버전의 오류/idle fallback을 먼저 규정한다. 현재 SVG 자산을 재사용할 수 있으면 유료 생성이나 전체 raster 교체부터 하지 않는다.

프레임 전환은 renderer에서만 수행하며 IPC·파일 저장·모델 호출을 매 프레임 실행하지 않는다. 창 bounds와 hit 영역은 공통 캐릭터 envelope 기준으로 유지해 이전 안내 깜빡임 문제가 돌아오지 않게 한다. 숨김·잠금·reduced-motion·캐릭터 교체·크래시에서는 재생을 멈추고 수명 종료 시 timer/bitmap/ObjectURL을 해제한다. 작업/승인 상태가 장식 동작보다 우선한다. 프레임별 별도 crop 때문에 피벗이 바뀌지 않도록 contact sheet와 실제 출력에서 확인한다.

universal-modder의 asset-pipeline에서 참고한 것은 규격·투명도·동일 피벗·재읽기 프리뷰·작은 실제 실행 검증이다. um/fal/Blender를 앱의 runtime requirement로 넣지 않는다. 현재 코드로 표현할 수 있는 SVG는 유지하고 다른 제작 도구는 실제 필요한 시점에 선택한다. [참고 스킬](https://github.com/rehan-remade/universal-modder/blob/main/skills/asset-pipeline/SKILL.md)

배율은 50% 기본과 기존 위치 anchor를 유지하면서 별도 변경으로 작업한다. 애니메이션과 창 기하를 한 번에 크게 바꾸지 않는다. 먼저 배율 후보 35/50/65%에서 메뉴·포인터·안내·미니 위치를 검사하고 값 범위를 확정한다. 장식 움직임이 아니라 사용자가 크기를 바꾼 경우에만 창 치수를 갱신한다.

Windows 네이티브 확인은 후반의 필수 완료 기준이지 macOS 모의 테스트로 대체하지 않는다. 가능하면 두 OS의 네 모서리·Snap/타일링·100/125/150/200%·혼합 DPI·모니터 연결/해제·잠금/절전·Tray·한글 입력·CLI 취소·패키징을 작은 시나리오로 확인한다. Windows 환경이 없으면 공통 소스/분기 검증은 계속하되 해당 수용 항목을 미검증으로 남긴다.

**수용 테스트:** v1/v2 fallback·잘못된 frame rect·0/음수 duration·프레임/fps/픽셀 예산 초과·정적/움직임 줄이기; center/edge의 hover/안내 토글에서 move/resize 0; 빠른 교체·드래그·메뉴 3초 숨김·미니/전체 초안; 배율/혼합 DPI·클릭 통과·앱 재시작 위치 보존. 실제 최종 번들에서 같게 통제한 idle/reduced/hidden 자원 비교를 하고 배터리 결과와 CPU 표본은 구분한다.

코멘트는 비자명한 순서/복구 이유만 남기고 구현을 그대로 읽어주는 주석이나 완료된 임시 TODO를 추가하지 않는다. ESLint/CSS 검사는 유지하며 파일을 여러 helper로 나누는 것 자체를 최적화라고 평가하지 않는다. generated bundle은 직접 편집하지 않고 build로 갱신한다. 모델/연결·저장 모듈의 책임이 다른 만큼 필요 없는 통합도 하지 않는다.

검증은 변경 범위에 맞춰 수행한다. G1은 pack/buddy fixture+해당 이미지/스킨 UI, G2는 stability/timing+큐/승인, G3/G4는 buddy/history/deletion+실패 주입, G5는 floating/pet-notice+플랫폼/자원 검증을 우선한다. 관련 실패나 새 계약 변경이 없으면 동일 검사를 무의미하게 반복하지 않는다. 단순 색상 변경에 구현을 복제하는 테스트를 늘리지 않고 팔레트 수치·실제 표시를 확인한다. 데이터/복구/경쟁은 의미 있는 회귀 테스트를 추가한다.

실제 모델 호출은 protocol/말투 전달 경계가 바뀌었을 때만 짧은 격리 질문으로 확인한다. UI 색상·asset 검증·프레임 재생에는 필요 없다. 사용자 실제 대화를 실패 주입/삭제 테스트로 사용하지 않는다. 실제 CLI 삭제 확인이 필요한 경우 검증용으로 생성한 세션의 출처/폴더/ID를 먼저 대조한다.

각 묶음 끝에서 source check/lint·관련 테스트·문서 계약을 갱신하고 staging package의 source/worker/version과 사용자 설정·대화 보존을 확인한다. 기존 실행 앱의 안전한 종료와 native 확인이 가능한 때만 최종 앱 교체를 수행한다. 되돌릴 때는 그 묶음에서 소유한 파일/등록 항목만 복구하며 다른 기존 변경을 reset하지 않는다. 새 저장 schema를 추가했다면 앱 파일만 이전 버전으로 바꿔도 호환된다고 가정하지 말고 schema/backup 복구 절차를 확인한다.

### 이번 작성 결과와 다음 착수 범위

이번에 완료한 것은 코드 재확인, 공식 형식/API 대조, 기준 검사와 상세 계획이다. 바로 구현할 권장 첫 묶음은 **M02 + M01-A**, 그 다음은 **M01-B decode probe/검증 → M03/M04 최소 상태 정책**이다. 픽셀 예산·decoder/애니메이션 이미지 호환·모드 registry/pack transaction은 위 선행 기준을 만족시킨 뒤 확정한다. 문서의 수용 기준은 앞으로 수행할 항목이며 이미 통과한 검사로 표시하지 않는다.

M10의 문맥/장기 기억, M11의 음성/목적 템플릿, M12의 Live2D/VRM·배회·다중 캐릭터, Slack S01–S17과 중앙 FIFO는 대기한다. 기능 수를 늘리기 위한 SDK/DB/브로커/범용 모딩 엔진 도입은 이번 계획에 포함하지 않는다.

### 예외와 복구

- PNG/WebP header 통과와 실제 decode를 구분한다. 손상 PNG·불완전 SVG·v2 캔버스 불일치·timeout을 실제 decoder로 거절했다. APNG와 animated WebP의 2프레임 fixture는 정적 대표 이미지로 바뀌는 것을 확인했다. 컨테이너 모든 프레임 재생/모든 손상 형태를 검증했다는 뜻은 아니다. [PNG 규격](https://www.w3.org/TR/png-3/), [WebP 규격](https://developers.google.com/speed/webp/docs/riff_container).
- UTF-8이 깨진 기본 MD도 원본 바이트를 백업한 뒤 제공 템플릿으로 복원한다. 등록부가 외부에서 바뀌거나 생성 journal의 MD가 바뀌면 덮어쓰지 않는다. 저장 중 사용자가 다른 MD로 이동/추가 편집하면 제출한 항목만 저장하고 새 초안은 지우지 않는다. 미저장 MD 초안은 앱 종료/renderer crash에서 영속 보존하지 않는다.
- 사용자 모드 보관은 MD를 지우지 않는다. 현재 선택 모드는 다른 모드를 고른 후 보관하고 제공 모드는 복제하여 개인화한다. registry/MD 생성 실패의 재시작 복구를 확인했다. 복구 불가능한 registry는 원본을 유지하고 MD 폴더/다시 읽기로 안내한다.
- 팩 교체는 여러 파일/설정 전체의 원자 교체가 아니다. 단계 journal로 이전 선택/팩/생성 템플릿을 복구하고 다른 사용자 파일은 삭제하지 않는다. 변조/추가 파일·복구 저장 실패는 원본/저널 보존과 write block으로 남긴다. 전원 상실 내구성/fsync·Windows 실기 파일 잠금은 별도 검증이다.
- 미리보기 중 원본 수정은 검증한 byte snapshot에 영향을 주지 않는다. 기본 팩 덮어쓰기, 만료 후보 적용, 확인 없는 동일 ID 교체는 거절한다. export는 참조 파일만 포함하고 편집 MD 포함은 기본 꺼짐이다.
- 잠금은 실제 응답 완료를 표시 완료로 기록하지 않는다. 절전은 현재 질문을 중단하고 대기 질문을 복귀 후 자동 실행하지 않는다. 일시 정지 큐의 `계속`/취소를 사용한다. 이 정책은 자체 Electron 이벤트 주입으로 확인했으며 OS 실절전으로 검증한 결과는 아니다.
- 최종 네이티브 확인에서 최초 숨김 패널의 목록 캐시만 채워지고 카드 DOM이 비는 문제를 발견했다. 목록을 dirty 상태로 기억하여 처음 보일 때 만들도록 수정했고, hidden sync → show 회귀를 추가했다. renderer crash/reload도 기존 대화/질문을 재실행하지 않는다.
