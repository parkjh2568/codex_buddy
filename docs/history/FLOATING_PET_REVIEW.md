# 플로팅 펫 동작 비교

검토일: 2026-10-06. 현재 옹기봇 alpha.8과 `/Users/jhpark/code/PokeTokenBar`의 `FloatingPetPanel.swift`를 읽고 비교했다. 실행 코드·배포 앱·사용자 위치는 변경하지 않았다. 가장자리 타일링과 Dock 겹침은 실제 데스크톱에서 재현 검증하지 않았다.

후속 요청으로 alpha.9에서 Electron 기반 수정과 macOS 네이티브 검증을 진행했다. 아래 내용은 수정 전 비교 기록이며 현재 변경·검증 범위는 [플로팅 버디 보완](FLOATING_PET_UPDATE.md)을 참고한다.

### 이동 제한 — 코드에서 확인

옹기봇은 시작 위치, 드래그, 말풍선 창 크기 변경의 세 경로에서 모두 `workArea` 기준으로 좌표를 제한한다. `workArea`는 전체 화면 범위가 아니라 메뉴 막대·Dock 등을 제외한 영역이다. 캐릭터만이 아니라 투명 여백을 포함한 창 전체를 제한하므로 캐릭터가 경계에 도달하기 전에 이동이 멈출 수 있다. 이는 현재 구현의 정책이며 PokeTokenBar의 이동 정책과 다르다.

### 가장자리의 블록 확대 — 원인 후보

현재 옹기봇 코드에는 화면 가장자리에 붙으면 반쪽 화면으로 확대하는 기능이 없다. 말풍선 표시로 창이 120×143에서 196×195로 바뀌는 자체 동작은 별도로 존재한다. 그보다 큰 사각 영역의 확대 미리보기가 나타난다면 macOS 창 타일링 또는 외부 창 관리 프로그램의 동작을 우선 확인해야 한다.

옹기봇은 일반 창을 사용하고 `resizable:false`만 지정한다. PokeTokenBar처럼 비활성 패널을 사용하지 않으며 최대화·전체 화면 허용도 명시적으로 끄지 않았다. 따라서 창 속성 차이는 원인 후보지만, 현재 조사만으로 타일링의 정확한 트리거를 확정하지 않는다. Electron은 macOS `type:'panel'`에서 비활성 패널 스타일을 적용하는 옵션을 제공한다. 실제 AppKit `NSPanel`과 동일한 클래스 구현이라고 가정하지 않는다. [Electron 창 유형·옵션](https://www.electronjs.org/docs/latest/api/base-window)

## 권장 수정 범위 — 아직 미착수

1. **캐릭터 창만 플로팅 방식으로 전환:** macOS `type:'panel'`과 최대화·전체 화면 비허용을 후보로 검증한다. 대화창은 키보드 입력이 가능해야 하므로 캐릭터 창과 같은 비활성 정책을 일괄 적용하지 않는다.
2. **드래그의 강제 경계 보정 제거:** Dock 영역·화면 끝을 향한 사용자 이동을 허용한다. 물리적인 화면 바깥에서는 그림이 잘리며, 다른 연결 화면으로 넘어갈 수 있는지 확인한다.
3. **펫 위치를 기준으로 말풍선 배치:** 말풍선 때문에 캐릭터를 화면 안쪽으로 밀지 않는다. 필요하면 말풍선 방향/위치만 바꾼다. 기존 투명 영역의 클릭 통과를 유지한다.
4. **복원과 구조 분리:** 드래그 중에는 자유롭게 이동하고, 재시작·모니터 분리 등으로 캐릭터가 보이지 않을 때만 복구한다. 트레이에 “버디 위치 초기화”를 추가해 직접 복구할 수 있게 한다.
5. **시스템 이동과 앵커 동기화:** 현재 move 이벤트는 저장값을 앵커에서 계산한다. 앱 밖에서 창 위치가 바뀌면 앵커가 실제 창 좌표와 달라질 수 있으므로 시스템 이동·크기 변경 경로도 검증한다.

전체 UI를 Swift로 재작성하는 작업부터 시작할 필요는 없다. Electron의 캐릭터 창 정책과 좌표 제한을 먼저 수정·검증하고, 필요한 동작이 충족되지 않을 때 작은 macOS 네이티브 오버레이/브리지를 검토한다.

## 위치와 표시 레벨의 구분

Dock 영역으로 옮길 수 있는지와 Dock보다 위에 그려지는지는 별개다. PokeTokenBar의 `.floating`과 Electron의 기본 floating 레벨은 Dock보다 위에 표시하겠다는 설정이 아니다. Dock이 캐릭터를 가릴 수 있다. 사용자 요구가 Dock 위 표시까지 포함되는지는 별도 결정사항이다. [Electron 표시 레벨](https://www.electronjs.org/docs/latest/api/base-window#winsetalwaysontopflag-level-relativelevel)

또한 Electron의 macOS 좌표 API에는 상단 y 좌표 제약이 문서화되어 있다. `workArea` 제한을 없애거나 `screen.bounds`를 사용한다는 이유만으로 모든 방향의 화면 밖 이동이 완전히 허용된다고 보장하지 않는다. 실제 macOS에서 확인해야 한다. [Electron 좌표 제약](https://www.electronjs.org/docs/latest/api/base-window#winsetboundsbounds-animate)

## 필요한 실제 검증

- Dock이 아래·왼쪽·오른쪽에 있는 경우와 자동 숨김 상태에서 드래그.
- 네 모서리의 부분 화면 밖 배치, 다른 모니터 이동, 모니터 분리 후 복구.
- 가장자리에서 OS 타일링 미리보기/크기 확대 여부와 앱의 자체 말풍선 확장 구분.
- 말풍선 켜짐/꺼짐·캐릭터 교체 후 캐릭터 원점 유지.
- 캐릭터 클릭으로 대화 열기, 드래그 시 뒤쪽 앱의 포커스 유지, 투명 여백 클릭 통과.
- 전체 화면·Spaces 전환, 재시작 복원·트레이 위치 초기화.

기존 클릭 통과 검증은 화면 중앙의 조건을 사용한다. 드래그 검증만으로 OS 타일링·Dock·화면 경계의 적합성이 확인됐다고 볼 수 없다. 위 조건은 수정 이후 별도로 재현해야 한다.
