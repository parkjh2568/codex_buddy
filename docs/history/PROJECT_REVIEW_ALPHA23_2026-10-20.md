## 유지하는 결정

단순 상태/문자열/화면 로직은 함수 안에 둔다. CLI 프로세스, 저장 워커, 인증 시도, 이미지 decode, 첨부 사본, 팩/MD 복구는 소유권과 실패 경계가 달라 별도 모듈을 유지한다. 캐릭터 팩과 스킨은 실행 코드 없는 데이터다.

Electron·renderer 번들·Markdown 정제는 실제 창/프로토콜/저장 요구를 처리한다. 현재 사용 중인 의존성을 추측으로 제거하거나 작은 함수를 범용 도구로 재분리하지 않는다. 런타임 교체·DB·브로커·플러그인 프레임워크는 현재 정리 범위에 추가하지 않는다.

### 구조·결합도·유지할 경계

[구조도와 상태 흐름](../ARCHITECTURE.md)에 main→stdio 연결, 저장/검색 worker, 데이터형 팩·MD·이미지 검증 경계를 갱신했다. 로컬 정적 require/import 순환은 없었다. main의 큰 IPC 분기와 renderer 상태 반영 콜백은 결합도 높은 중심이지만 단순 분리로 큐/저장 순서를 숨기지 않는다. 접수 직렬화와 실행 FIFO, 소유 프로세스/대화/턴, 창 generation, revision, 저장 완료 후 cursor 확정이 핵심 불변조건이다.

다음 책임이 실제로 바뀔 때만 모듈을 나눈다: 외부 프로세스/인증 수명, 파일 쓰기·복구 소유권, 이미지 decode, 검색 worker. 작은 변환·검사·조건문을 새 헬퍼나 범용 dispatcher로 추출하지 않았다. 첨부 입력 경로의 반복 검사는 preload의 trusted event, main의 소유 창·대화, 파일 보관 경계에서 서로 다른 조건을 검증하므로 일괄 제거하지 않는다.

외부 동일 사용자 프로세스와의 filesystem 변경은 완전한 OS compare-and-swap 트랜잭션을 제공하지 않는다. 수정은 확인한 충돌에서 자동 덮어쓰기/삭제를 멈추고 보존하는 방향이다. 알 수 없는 잔여 파일을 깨끗이 보이게 하려고 삭제하지 않는다. Windows에서 POSIX FIFO 동작과 macOS 실물 전원/입력 검증까지 통과했다고 해석하지 않는다.

독립 리뷰에서 첨부·응답 이미지 임시 파일의 무조건 정리도 같은 소유권 문제로 되돌려 수정했다. 이름 충돌·같은 inode의 외부 편집 4개 재현은 FD identity와 완전한 내용 대조 뒤에만 정리하도록 바꿨다. 부분 쓰기나 외부 파일은 남긴다. quota 조사에 yield를 추가한 뒤 먼저 조사한 파일이 폴더 시각 변경 없이 512MiB로 커지면 새 이미지 73바이트가 초과 저장되는 경합도 재현했다. 양쪽 캐시에 파일별 stat snapshot을 두고 마지막 yield 이후 다시 대조해 쓰기를 거절한다. 이 최종 동기 확인 비용은 신규 쓰기에 남는다.

반대로 실제 검증의 늦은 턴 완료 필터 누락 의심은 연결 모듈 전체를 다시 읽어 기존 소유 턴 필터를 확인한 뒤 차단 이슈에서 제외했다. 검증 fixture의 완료 ID를 실제 계약에 맞추고 최소 결과 대조만 보완했으며 중복 이벤트 버퍼를 추가하지 않았다. 의심만으로 프로덕션 결함이나 필수 리팩터링으로 확정하지 않는다.

### 저장 읽기와 백업의 정지 방어

[Store](../../src/store.cjs)의 읽기 open 6곳에 플랫폼 지원 시 `O_NONBLOCK`을 적용했다. 복구 payload 반복문이 최종/임시 파일을 각각 읽으므로 실제 재현 대상은 7개다. 기존 일반 파일·링크·FD identity·읽기 전후 변경·크기·UTF-8·저널 hash 검사를 유지했다. POSIX 격리 자식 프로세스의 7개 대상과 worker 경계 2개가 watchdog 안에서 끝나고, 오류 시 원본·저널·FD 정리를 확인했다. Windows의 FIFO 동작까지 검증했다는 의미는 아니다.

flag만 바꾼 첫 시도는 생성자 오류 처리의 `copyFileSync`가 원본을 다시 열면서 여전히 정지했다. 원본을 안전하게 모두 읽고 FD/path 검증을 통과한 바이트를 보관해 설정 복구·v1 이관·오류 백업에 쓴다. 안전한 원본을 확보하기 전에 실패하면 쓰기를 차단하고 원본·저널을 남기며 삭제 복구를 이어 실행하지 않는다. 읽기가 끝난 뒤 경로를 FIFO로 교체한 설정/v1/JSON 오류 3개 추가 재현도 독립 검토했다. BOM·잘못된 UTF-8 백업은 검증한 원본 바이트 그대로 유지한다. [저장 근거](../../artifacts/followup-implementation-2026-10-20/storage/verification.json), [독립 리뷰](../../artifacts/followup-implementation-2026-10-20/protocol/store-independent-review.json)를 따른다.

### P01·P07: 분리 계측과 내보내기 복사

MD 내보내기는 선택 시점의 전체 메시지를 `structuredClone`하는 대신 실제 출력 필드만 인라인으로 복사한다. 긴 불변 문자열을 공유하고 첨부/이미지 배열과 출력 metadata는 새 객체로 만든다. 제목과 출력 내용은 선택기가 열려 있는 동안 원본이 바뀌어도 접수 시점 값을 유지한다. 독립 리뷰에서 예전 기록의 객체/배열형 `error`가 참조 공유되는 퇴행을 재현해, 해당 값만 선택적으로 깊게 복사하도록 수정했다. 불필요한 metadata getter는 읽지 않고 예전 오류 배열·첨부/이미지 변경·부분 실패 보존을 회귀로 확인했다.

[전후 원시 표본](../../artifacts/followup-implementation-2026-10-20/export/benchmark.json), [독립 수치·코드 검증](../../artifacts/followup-implementation-2026-10-20/protocol/export-independent-review.json)을 따른다.

### P04: 캐시 접수 범위의 quota 소유권과 반복 조사

[CacheQuotaBatch](../../src/cache-quota.cjs)는 실제로 다른 소유권 경계인 canonical root별 쓰기 직렬화·한 호출의 사용량 snapshot만 맡는다. 첨부/이미지 형식·decode·내용 hash·임시 FD·부분 실패 정리는 기존 클래스에 둔다. 첫 전체 조사 뒤 같은 접수에서 성공한 신규 파일만 snapshot/사용량에 더한다. 매 비동기 staging 뒤에는 현재 목록 수·독립된 소유 임시 파일·기존 모든 파일의 dev/ino/size/mtime/ctime와 root를 **동기적으로 재검사한 뒤** publish한다. 폴더 mtime만 믿거나 내용 hash를 건너뛰지 않는다. 다른 프로세스의 변경까지 원자적으로 잠그는 OS 트랜잭션은 아니다.

같은 root의 여러 인스턴스·파일/이미지 저장은 소유권을 공유하고 다른 root는 병렬로 진행한다. 파일→이미지→파일은 파일 root를 해제하고 다시 획득해 같은 root의 중첩 대기를 막는다. 잔여 임시 파일은 snapshot을 무효화하고 다음 항목에서 실제 디렉터리를 재조사한다. same-inode 성장/같은 파일 수의 삭제+외부 추가/임시 파일의 외부 교체·부분 성공·오류 뒤 lock 해제를 회귀와 독립 리뷰로 확인했다. 이미 시작한 I/O를 취소하는 새 AbortSignal API는 추가하지 않았으며, 상위 작업이 취소돼 남은 소유 캐시는 미참조 자료로 보존될 수 있다.

첫 후보는 8개 총시간이 개선돼도 신규 1개 지연이 커져 반송했다. 최종 확인 루프에서 경로 재계산·Map lookup·키 배열/closure 할당을 없애고 필요한 scalar metadata만 보관했다. 현재 목록 수와 독립 임시 파일을 확인하고 기존 파일 전부의 존재/identity를 검증하면 목록 전체를 소진한다는 조건을 독립 리뷰했다. 최종 자료는 0/1,000/10,000개×1/8개×신규/재사용×파일/이미지의 **24조건×전후 20표본=960개**이며 실행 순서를 교차했다.

10,000개 캐시의 8개 신규 첨부는 중앙값 **780.89→439.26ms**, p95 **861.58→476.74ms**, 이미지는 중앙값 **711.86→400.96ms**, p95 **760.76→415.23ms**였다. 두 경로의 `lstat`은 **160,744→90,196회**다. 재사용 첨부 8개는 중앙값 **723.41→0.658ms**, 전체 조사 8→0회이며 매 파일 내용은 계속 hash 검사한다. 재사용 이미지는 기존 전체 조사 0회·stat 32회를 유지했다. 신규 8개 디렉터리 목록 읽기는 8→9회이므로 모든 종류의 I/O가 감소했다고 하지 않는다.

최종 20표본 중 신규 이미지 1개의 p95가 **187.77→239.47ms(+27.5%)**로 사전 25% 기준을 넘었다. 이 실패·모든 outlier를 보존한 채 동일 소스로 별도 40쌍 확인과 원본 포함 60표본/버전 합산의 기준을 실행 전에 고정했다. 확인 p95는 **97.71→101.06ms**, 전체 60표본 p95는 **105.94→104.91ms**로 기준을 통과했다. 이 합성 관찰이 실제 서비스 p95의 통계적 보장이라는 의미는 아니다.

신규 1개가 더 빨라졌다는 주장은 하지 않는다. 합산 중앙값은 **93.32→97.68ms**였고 1ms timer 최대 간격의 표본 p95는 **41.58→47.91ms**로 늘었다. 마지막 O(N) 검사를 publish 직전까지 유지한 비용과 남은 main blocking을 명시한다. 채택 범위는 다중 첨부 총시간·반복 stat·재사용 파일 비용 감소와 강화된 최종 검증이다. validator stub·warm filesystem·합성 파일을 사용했으며 실제 Electron decode·OS 포인터·최대 RSS는 이 벤치가 측정하지 않는다. [최종 960표본](../../artifacts/followup-implementation-2026-10-20/cache/matrix-final.json), [확인 계획](../../artifacts/followup-implementation-2026-10-20/cache/confirmation-plan.json), [확인·전체 합산](../../artifacts/followup-implementation-2026-10-20/cache/confirmation-analysis.json), [최종 코드 독립 리뷰](../../artifacts/followup-implementation-2026-10-20/protocol/cache-final-independent-review.json)를 따른다.

### P05·P06: 현재 계약을 유지한 결정

25턴×40페이지 fixture는 최종 1,250,589 bytes에 성공한 `writeFileSync` payload 25,663,250 bytes/120회, 약 **20.52093배**였다. 같은 크기로 증가하는 전체 snapshot을 매 페이지 확정하면 하한 `(P+1)/2`가 20.5배다. append log/불변 페이지 파일은 upsert·순서·검색·내보내기·캐시 참조·삭제·구형 읽기/복귀 설계가 필요하고, 호환 snapshot을 매번 쓰면 증폭이 남는다. batch 확정은 UI/cursor 수용 시점도 늦춰야 하므로 현재 계약의 숨은 debounce로 도입하지 않았다. cursor는 현재 메모리 값이며 저장 성공 후 전진하고, 재시작은 처음 페이지를 재조회해 ID 중복을 제거한다. 물리 디스크 쓰기·전원 상실 내구성을 측정한 수치가 아니다. [대안과 복구/호환 조건](../../artifacts/followup-implementation-2026-10-20/storage/p05-decision.json)에 비교했다.

로컬 CLI `0.163.0-alpha.10.2`의 정적 schema/help를 조사했다. 172개 ClientRequest에 bulk read/delete는 없지만, `thread/list`에는 `ancestorThreadId`·`parentThreadId`가 있다. 구형 schema에는 없고 archived/source 기본 필터·기능 감지·전체 조회 완결성·확인 후 삭제 cascade 계약이 충분히 확인되지 않았다. “관계 API가 없다”로 결론 내리지 않는다. 삭제 관계 최대 4개 동시 read와 기존 소유권·deadline·실패 보존 경로를 유지했다. 실제 RPC/모델/삭제/로그인/네트워크 호출은 0건이다. [P06 계약 판단](../../artifacts/followup-implementation-2026-10-20/protocol/p06-contract.json)을 따른다.
