# my_budy 제품 방향과 구조 검토

2026년 10월 10일 기준, 프로젝트를 맡은 기획자·개발자의 관점에서 시작한 문제, 설계 전제, 최근 제품 변화, 현재 구조의 이점과 유지 비용을 검토했다. 근거는 사용자 요청, 현재 코드, 기존 기획 기록과 직접 열어 확인한 공식 문서다. 시장 점유율·사용자 만족도·다른 제품 대비 성능을 측정한 보고서는 아니다.

## 시작한 문제와 첫 질문

대화에서 직접 확인한 불편은 **초보자가 CLI 연결을 복구하기 어려움**, **생성된 이미지가 대화에 나타나지 않음**, **이미지·파일을 질문에 함께 넣고 싶음**, **작업 중 작성한 후속 질문을 잃지 않고 FIFO로 처리하고 싶음**이다. 사용자도 이 프로젝트를 `my_budy`라는 버디 프로젝트로 명시했다. 캐릭터·이름·말투를 유지하면서 필요한 도움에 쉽게 접근하는 방향이 현재 README·TASKS와 맞는다.

시작 계기는 질문·자료 전달·기다림·결과 확인 과정의 마찰을 줄이려는 것으로 해석한다. 화면 전환 부담과 결과 누락에 대한 불확실성이 영향을 줬다는 것은 이 요청에서의 **추론**이다. 특정 업무 사고나 매출 문제가 있었다고 단정할 근거는 없다. [기존 기획 기록](history/PROJECT_REVIEW.md)도 빠른 바탕화면 질문과 개인 캐릭터를 중심으로 설명한다.

내가 처음 묻는 질문은 **“마지막으로 질문·자료를 전달하거나 답변을 확인하다 막혔던 순간에, 어디서 무엇이 어려웠고 어떻게 해결했나요?”**다. 이 사례를 알아야 복구 안내, 입력 보존, 상태 관찰, 캐릭터 취향 중 어디에 시간을 써야 할지 결정할 수 있다. 그다음은 버디를 끈 상태에서도 이 앱을 선택할 이유, 주로 쓰는 OS·작업 폴더, 개인용과 타인 배포의 범위다.

이번 작업에서는 주된 가치가 CLI 편의성인지, 버디 경험인지, 코드 작업 관리인지 선택형 질문을 함께 제시했다. 답변을 받기 전의 우선 가설은 기존 요청에 맞춘 **연결·첨부·이미지·대기열의 신뢰성과 조용한 개인 버디**다. 이를 사용자 선호가 확정된 것으로 쓰지는 않는다.

## 접근에 깔린 전제

| 전제 | 현재 근거 | 확인할 방법 |
|---|---|---|
| 버디가 질문까지의 마찰을 줄인다 | 한 번 클릭/단축키의 미니 대화, 일반 대화와 같은 기록 | 실제 자주 하는 질문 5종에서 입력 시작까지의 시간·동작 수 비교 |
| 캐릭터와 말투가 재사용 동기를 높인다 | 이름·SVG 팩·MD 말투·정숙 프로필 구현 | 캐릭터를 켜고 끈 두 사용 흐름에서 선호와 방해 사례 확인 |
| FIFO가 후속 질문을 안전하게 처리한다 | 최대 10개, 접수/저장/실행 순서, 모델·말투·폴더 snapshot | 긴 첫 질문 뒤 추가·수정·취소·재연결의 순서와 재입력 여부 확인 |
| 로컬 제어가 가치가 있다 | 기록/첨부 사본을 로컬에 보관하고 CLI 설정·계정을 재사용 | 저장 위치·보내는 자료·복구 방법을 사용자에게 설명 가능한지 확인 |
| 읽기 전용이 현재 목적에 충분하다 | 추가 권한은 개별 승인, 계획·리뷰·분석·대화 중심 | 실제로 필요한 행동이 설명/분석인지 파일 수정인지 사례로 구분 |
| 작은 버디의 상시 비용을 감수할 수 있다 | Electron 창·CLI·80ms pointer와 제한된 애니메이션 | 같은 기기에서 버디 숨김/정숙/일상 상태의 CPU·메모리·배터리 비교 |

로컬 저장과 모델의 오프라인 실행은 다른 조건이다. 현재 응답은 연결한 CLI의 계정·네트워크·제공자에 의존한다. 기록 사본을 만들고 초안을 보존하는 과정도 사용자가 전달을 선택한 자료를 중심으로 한다. 자동 화면 수집이나 기억·상시 외부 메시지 수집은 현재 구현 범위가 아니다.

FIFO는 실행 순서를 예측하기 쉽지만 긴 앞 작업이 뒤 질문을 기다리게 한다. 사용자가 현재 작업의 방향을 고치는 것을 원할 때는 별도 steering 계약이 필요하다. 기존 요청대로 후속 질문은 대기열에 두며, 편의성을 이유로 진행 중 작업에 자동 삽입하지 않는다.

## 최근 제품 변화와 my_budy의 위치

아래는 2026년 10월 10일에 확인한 공식 제품 문서와 공개 업데이트다. 공개 기능 설명이 사용자의 계정·배포 환경에서 동일하게 제공됨을 검증한 것은 아니다. 표의 my_budy 판단은 이 사실에 대한 설계 추론이다.

| 관찰한 변화 | 직접 확인한 사실 | my_budy에 대한 판단 |
|---|---|---|
| 캐릭터가 작업 상태를 보여주는 접점으로 사용됨 | ChatGPT 데스크톱 Pets는 floating controls에서 대화를 시작하고 입력 필요·완료·실패 상태를 표시. 해당 controls의 새 대화는 프로젝트 밖에서 시작함. [Pets](https://learn.chatgpt.com/docs/pets) | 캐릭터 표시 자체의 차별성은 작다. 같은 로컬 작업 폴더·대화를 유지하는 미니 흐름과 직접 편집 가능한 SVG/MD 계약을 검증할 가치가 있음 |
| 빠른 입력을 긴 대화로 연결함 | Raycast Quick AI는 검색 창에서 답하고 같은 창에서 후속 대화를 이어가며 AI Chat으로 전달할 수 있음. [Quick AI](https://manual.raycast.com/ai/quick-ai) | 입력 단축과 복사·자료 첨부·결과 활용이 우선. 이런 흐름이 더 불편해지면 옵션을 늘리는 가치도 줄어듦 |
| 실행의 격리·검토·방향 변경을 지원함 | Codex 문서는 Queue와 Steer를 구분. Claude Desktop은 독립 세션과 Git worktree를 설명함. [Codex의 Queue/Steer](https://developers.openai.com/blog/mastering-codex-remote-for-engineering), [Claude Desktop](https://code.claude.com/docs/en/desktop) | 현재 개인 FIFO의 목적과 실행 권한을 명료하게 유지. 파일 수정·다중 세션 요구가 구체화되면 격리와 승인부터 설계 |
| 지속 책임과 여러 기기의 접근으로 확장됨 | OpenAI의 10월 5–9일 업데이트는 Dots 설정과 외형, 9월 28–10월 2일 업데이트는 지속 작업·기기간 흐름을 설명함. [최근 업데이트](https://learn.chatgpt.com/docs/whats-new) | 개인 로컬 앱의 상시 서버·동기화·자동 수집을 지금 추가할 근거는 부족. PC가 꺼진 상황까지 책임져야 하는 요구부터 확인 |

따라서 방향은 **개인 작업 흐름을 직접 통제하는, 작고 조용한 로컬 버디**다. 일반적인 질문과 캐릭터 표시만 필요하다면 기존 제품도 선택지가 된다. my_budy를 계속 만드는 이유는 원하는 데이터 팩·말투·고정 폴더·자료 사본·복구 및 보류 정책을 직접 관리하고 그 경험을 검증할 수 있다는 데 있다. 이것이 공식 앱보다 낫다는 결론은 아직 사용자 비교 자료가 필요하다.

## 현재 구조와 라이브러리를 쓰는 이유

| 선택 | 현재 쓰는 이유 | 비용과 변경 조건 |
|---|---|---|
| Electron | Node 기반 CLI/파일/worker와 창·트레이·클립보드·알림을 같은 앱에서 처리. 현재 플랫폼 및 실패 경로의 검사 축적 | 상주 프로세스·런타임 배포·서명 비용. 실제 자원 기준을 넘는지 먼저 측정 |
| 로컬 Codex app-server | 모델 목록·인증·턴·승인·이미지 결과를 구조화된 이벤트로 연결. CLI 설정 파일을 앱이 덮어쓰지 않음 | 설치 CLI·계정·실험 API 호환성과 프로세스 수명을 관리해야 함 |
| 직접 DOM/CSS/SVG | 작은 미니 대화와 7개 상태 캐릭터를 기존 웹 자산으로 표현. 변경된 메시지/진행/큐만 갱신 | renderer 수명과 입력 상태의 조건이 늘면 명시적 상태 표와 회귀가 필요 |
| markdown-it + DOMPurify | 모델의 Markdown을 표시하면서 raw HTML과 허용하지 않은 DOM 속성을 제외 | 파싱과 정제 비용. 기능 이름이 비슷하다는 이유로 둘 중 하나를 미사용으로 삭제하지 않음 |
| markdown-it-cjk-friendly | 실제 한국어 답변의 강조·문장 구성을 기존 Markdown 흐름에 맞춤 | 한국어 표시 회귀를 유지. 현재 import와 파서 사용처가 있음 |
| esbuild | renderer 의존성을 로컬 번들로 만들고 패키지에 고정 | 소스/번들/ASAR가 같은 코드인지 확인해야 함 |
| JSON + 직렬 저장 worker | 개인 단일 작성자 앱의 설정·대화·사본과 저널 복구를 기존 구조로 처리 | 큰 기록의 복사 비용, 완전한 DB 트랜잭션·전원 장애 내구성 보장은 없음 |
| 데이터 팩·MD | 외형·표정·말투 교체가 실행 코드나 모델 권한 증가를 동반하지 않음 | 팩 검증·원문 보존·hash/revision·편집/복원의 관리가 필요 |

Electron 공식 문서는 main의 Node API, 창별 renderer와 preload/context isolation을 설명한다. 이 프로젝트의 모듈 경계와 프로세스 책임은 그 구조에 맞는다. [Electron Process Model](https://www.electronjs.org/docs/latest/tutorial/process-model).

Tauri는 Rust와 OS WebView를 사용하는 대안이다. 번들 크기 관점의 이점은 있지만 현재 Node/worker·투명 창·다중 창·파일 입력·decode/클립보드 경로를 이관하고 플랫폼별로 재검증해야 한다. 실제 메모리·배터리 예산을 정하고 초과 원인을 측정하기 전에는 런타임 교체를 우선하지 않는다. 성능 우위를 숫자로 단정하지 않는다. [Tauri Architecture](https://v2.tauri.app/concept/architecture/).

현재 `private:true`인 개인 로컬 사용과 외부 고객에게 서비스를 제공하는 것은 인증 설계가 다르다. 공식 app-server 문서는 로컬/오픈소스 사용과 상업·호스팅 서비스를 구분하고 Sign in with ChatGPT 안내를 제공한다. 지금은 개인 CLI 설정을 유지하며, 배포 대상을 넓힐 때 공식 지원 형태와 가입·인증 UX를 먼저 확인한다. [Codex App Server의 인증 안내](https://learn.chatgpt.com/docs/app-server#auth-endpoints).

## 코드와 문서의 개선 우선순위

이번 검토로 재현한 R09–R12는 편집 진입 초안·fallback 설정·사용량 병합·연결 안내의 문제였다. [alpha16 검토](history/CHANGE_REVIEW_ALPHA16_2026-10-10.md) 이후 기존 모듈 안에서 수정하고 [이번 실행 결과](history/QUALITY_CYCLE_RESULT_2026-10-10.md)에 검증을 기록했다. 불필요한 저장 전 원본 읽기를 줄이고 인라인 들여쓰기를 정리했다.

| 다음 관심사 | 이유 | 구체적인 착수/완료 기준 |
|---|---|---|
| 최초 연결 실사용 | 가장 직접적인 요청이며 설치·계정·폴더 오류가 응답 전에 발생 | 새 계정/새 PC에서 안내만 따라 첫 질문, 중단·복구, 이미지 결과 확인. 인증 정보나 기존 질문을 다시 입력하게 하지 않는지 관찰 |
| UI 접근과 상주 자원 | 작은 앱의 가치는 빠른 접근과 낮은 방해에 있음 | 같은 기기의 warm open·숨김·정숙·일상 조건을 비교. UI 열림과 모델 첫/최종 응답을 별도 기록 |
| 큰 기록/이미지의 peak memory | 전체 CLI 기록과 MD 이미지 사본은 메모리에 보관 | C07–C09: 대표 크기에서 peak RSS·메인 지연·저장/내보내기 비용 측정 후 범위를 정해 개선 |
| 읽음과 실행 정보 의미 | 최신 unread 표시·첫 미리보기·누적 토큰은 실제 열람/현재 문맥 점유율과 같지 않음 | 표시 이름과 확인한 범위를 유지. 모든 메시지의 영속 읽음이나 문맥 점유율은 요구가 있을 때 별도 계약 |
| 입력/편집 상태의 증가 | await 사이 수명 문제는 UI와 main의 소유권 둘 다 필요 | 현재 코드의 상태와 전이 조건을 문서·회귀로 유지. 새 기능 전 허용/보류/완료/실패 시나리오 확인 |
| 문서의 현재/이력 구분 | README·TASKS·검증 보고서가 서로 다른 시점의 숫자를 가질 수 있음 | 최신 후보와 근거 링크를 같은 기준으로 갱신하고 날짜별 결과는 보존 |
| 외부 배포 | 사용 환경이 넓어지면 설치·업데이트·권한·인증 요구가 달라짐 | C10/O10의 Windows·Intel·새 환경·서명/공증·설치 수용을 실제 대상에서 확인 |

자동 기억·음성·Slack 상시 수집·현재 턴 steering·다중 worktree·3D 캐릭터는 별도 사용자 요구와 권한·수명·비용 조건이 있는 후속 기능이다. 기존 계획의 조건부 상태를 유지한다. 외형만 바꾸는 팩과 실행 권한을 가진 플러그인을 합치지 않는다.

## 데드코드와 과분리에 대한 판단

이번 변경에는 새 helper 모듈이나 런타임 의존성이 없다. 작은 문자열·입력·설정 처리는 기존 함수 안에 두었다. CLI 프로세스, Store/worker, 첨부/이미지, 팩 검증은 소유권과 실패가 달라 하나로 합칠 이유가 없다. 필요한 I/O의 비동기 처리와 단순 로직의 인라인 작성은 함께 지킬 수 있다.

새 편집 진입 객체의 중복 필드는 수정 후 재검토에서 제거했다. 새 기록에 쓰지 않는 reviewState 생성과 tokenUsage.updatedAt은 앞선 정리에서 줄였으며 과거 기록 검증은 남아 있다. 현재 사용 중인 의존성·팩 상태·검증 파일을 단순 개수나 이름만 보고 삭제할 근거는 없다.

검토 보고서와 복구 묶음은 당시 검증과 복원의 자료다. 최신 문서에서는 현재 결과를 앞에 두고 과거 문서에는 시점을 표시해 탐색 비용을 줄인다. 코드·문서·테스트의 중복과 백업의 보존 책임을 같은 기준으로 일괄 삭제하지 않는다.

이 프로젝트의 다음 투자는 실제 불편이 줄었는지와 상주 비용을 확인하는 데 두는 것이 타당하다. 요구를 만족하는 현 구조를 유지하면서 검증한 오류를 없애는 작업은 가치가 있고, 기능 수를 늘리는 것만으로 그 가치를 증명할 수는 없다.
