## 저장 방식과 복구

기본 위치는 `~/Library/Application Support/OnggiBot/`입니다. 설치 설정에 따라 실제 경로는 설정의 기록 폴더 열기로 확인합니다.

- `state.json`: 설정, 활성 대화 ID, 소유 대화 목록·제목·미리보기·Codex thread ID·작업 폴더 등.
- `conversations/<UUID>.json`: 질문·답변 원문, 실행 상태, 질문별 모델/추론/속도, 선택형 시간 측정치.
- `save-journal.json`: 두 파일의 저장이 진행 중일 때만 존재하는 복구 정보. 대상 소유 대화 ID와 state/history SHA-256 확인값을 기록합니다.

새 질문 접수, thread 생성/연결, 답변 완료·중단, 측정 확정, 대화 전환 때 저장합니다. 설정·위치만 바뀌면 대화 본문 직렬화를 생략합니다. 스트리밍 글자마다 저장하지 않으며 비정상 종료 직전 부분 답변은 로컬 파일에 없을 수 있습니다. CLI 자체 기록은 별도로 유지됩니다.

대화 파일이 바뀌면 대화 `.tmp`와 목록 `.tmp`를 준비하고 저널을 `.tmp`→rename으로 확정한 뒤 대화→목록 순서로 교체합니다. 두 교체가 끝나면 저널을 제거합니다. 다음 실행에서 남은 저널이 발견되면 staged/final 파일의 해시·크기·소유 관계를 확인하고 남은 교체를 마무리합니다. 새로운 형식의 대화 DB로 이관하지 않으며 기존 v2 JSON 기록을 유지합니다.

저널 확정 전 실패하면 새 대화 등록과 목록 변경을 메모리에서 되돌립니다. 새 대화/이전 대화로 바꾸는 단계의 저장 실패도 기존 활성 대화·메시지·설정으로 돌아갑니다. 저널 확정 뒤 실패하면 복구 파일을 보존하고 쓰기를 막아 다른 저장으로 덮어쓰지 않게 합니다. 접수 오류가 표시되었더라도 저널에 기록된 미전송 질문은 복구 뒤 중단 상태로 보일 수 있습니다. 이를 CLI에 자동 전송하지 않습니다.

완료 응답 저장 실패는 화면 답변을 유지하고 저장 오류를 표시합니다. 다음 대기 질문은 실행하지 않고 중단합니다. 디스크 오류를 해결한 뒤 재실행하면 보존된 저널을 복구합니다. 해시·소유·크기가 맞지 않으면 원본을 자동 삭제/덮어쓰지 않고 복구 필요 안내를 표시합니다. 오류 확인 전 기록 폴더를 보존하는 것이 필요합니다.

이 저널은 **파일 교체 도중 프로세스 종료의 복구**를 다룹니다. 모든 파일/디렉터리에 fsync하는 완전한 DB 트랜잭션이나 전원 장애 내구성 보장은 아닙니다. 이전 버전에서 이미 생긴 고아 파일을 자동으로 목록에 등록하지 않습니다. 저널 없이 남은 `.tmp`는 미확정 파일로 취급합니다.

기록은 평문이며 인증 토큰은 저장하지 않습니다. 대화 파일은 최대 32MiB, 목록 파일은 최대 8MiB입니다. 질문 접수 시 미완료 응답의 예상 공간을 예약해 초과 질문을 큐 등록 전에 거절합니다.

## CLI 프레임과 페이지 표시의 차이

기존에는 누적 문자열이 8×1024×1024자보다 크면 청크 안의 줄을 분리하기 전에 프로세스를 종료했습니다. 이제는 청크별 개행을 먼저 처리하고, 한 프레임의 UTF-8 바이트 수를 확인합니다. 여러 정상 프레임의 합계로 한도를 초과했다는 판정을 하지 않습니다. 부분 문자열을 배열에 보관하고 완성된 프레임에서 한 번 결합합니다.

기본 프레임 한도는 **64MiB**입니다. 큰 정상 응답을 처리하되 한도를 넘는 응답은 명확한 오류와 함께 연결을 종료하고 pending 요청을 정리합니다. 64MiB를 넘는 도구/전체 기록까지 보장하지 않으며 기록 저장 한도와 네트워크 프레임 한도는 다른 목적입니다.

화면은 최근 최대 100개 메시지부터 표시합니다. 한 묶음의 텍스트가 약 256KiB를 넘으면 개수를 더 줄입니다. 가장 최근 메시지 하나는 크더라도 표시합니다. `이전 내용 더 보기`는 이전 최대 100개/256KiB 묶음을 추가하며 보고 있던 위치를 보존합니다. 누르면 누적 DOM은 늘어납니다. 현재 방식은 단계 표시이며 완전한 DOM 가상화는 아닙니다. 보관 메시지 1000개를 100개로 삭제하지 않습니다.

메인 프로세스는 로드한 메시지의 텍스트와 작은 메타데이터를 비교해 변경된 항목만 `messagePatch.upsert`에 넣습니다. 렌더러는 ID 순서로 캐시를 갱신하고 카드 Map을 재사용합니다. 대화 변경·재개·렌더러 재시작에서는 캐시를 초기화합니다. 전체 대화를 다시 보내던 스트리밍 IPC와 카드별 DOM 전체 검색을 줄였습니다.

CLI의 `thread/turns/list`는 공식 문서상 실험 API이며 설치 CLI 생성 스키마에도 있습니다. 이번에는 실험 API 사용 범위를 넓히지 않고 로컬 표시와 프레임 처리를 개선했습니다. 실제 CLI 전체 기록 조회·재개는 여전히 별도 호환 검증 과제입니다. [공식 OpenAI App Server 문서](https://learn.chatgpt.com/docs/app-server)

## 측정 결과와 한계

`npm run smoke:performance`는 실제 모델을 호출하지 않고 별도 프로필에서 1000개 메시지를 생성합니다. 최종 검증 결과는 `artifacts/performance-ui-smoke.json`입니다.

| 값 | 결과 |
|---|---:|
| 전체 1000개 메시지 JSON | 1,757,281 bytes |
| 첫 100개 메시지 patch | 176,883 bytes |
| 200개 로드 상태의 한 답변 갱신 patch | 4,012 bytes |
| 내용 변경 없는 patch | 2,235 bytes / upsert 0 |
| 1000개 기록 저장 1회 | 약 14.50ms |
| 첫 100개 화면 준비 | 약 155.7ms |
| 100,000자 메시지 55개 상태의 첫 표시 | 2개 |

메시지 payload끼리 비교한 결과입니다. 실제 전체 IPC에는 설정·목록 등의 데이터도 있습니다. 최초 UI 준비에는 갱신 예약·IPC·DOM 작업·테스트 대기가 포함됩니다. 단일 조건의 기능/규모 검증이며 p95·장시간 배터리·평균 속도 향상율을 의미하지 않습니다. 1000개가 디스크에 모두 남는지, 이전 내용의 순서·스크롤, 재개 시 초기 표시량, 용량 초과 시 가짜 큐 항목이 남지 않는지도 확인합니다.

프로세스별 working set 스냅샷은 일반 1000개 기록 시나리오 뒤, 인위적인 용량 한계 시나리오 전에 수집합니다. 공유 메모리가 있으므로 합을 고유 RAM으로 해석하지 않습니다. 첫 CPU 조회의 0%도 유휴 CPU 검증 근거가 아닙니다.

핵심 테스트는 23개입니다. 별도의 timing smoke는 완료 저장 실패를 주입하여 앱이 계속 표시되고 다음 질문이 CLI로 전송되지 않는지 검증합니다. 모델·기록·Markdown·캐릭터·실제 Luna/high 왕복 회귀도 실시했습니다.

## 후속 작업 — Slack 이전 우선순위

1. **C07 저장 비동기화와 용량 계산**: 저장·SHA-256·파일 읽기는 아직 동기 방식입니다. 32MiB 근처 기록의 입력 지연을 측정한 뒤 직렬화 worker/비동기 저장 및 접수 순서 보장을 함께 설계합니다. 필요 없이 DB를 먼저 추가하지 않습니다.
2. **C08 장시간 리소스 평가**: 유휴 30분, 화면 숨김, 긴 기록, 캐릭터 움직임별 CPU/배터리 목표와 반복 측정.
3. **C09 CLI 기록 페이지 조회**: 실험 API 기능 확인, 커서 반복 방지, 지원하지 않을 때 로컬 기록 유지. 로컬 파일 자체의 페이지 읽기는 추가 설계가 필요합니다.
4. **C10 배포·권한 호환**: 서명/공증/자동 업데이트·다른 OS·다중 모니터·읽기 범위. 현재 Apple Silicon 로컬 알파의 범위를 유지합니다.
5. 이후 Slack 명시적 호출→키워드→중복/무음→뉘앙스 판단. 다중 클라이언트 FIFO는 실제 수요와 순서 정책 확정 후입니다.

C06 최종 전달: alpha.7 빌드 10을 실제 데스크톱에서 실행하여 기존 목록·모델·속도·측정 설정과 CLI 연결을 확인했습니다. 패키지 ASAR 크기는 646,017 bytes이며 renderer 의존성 원본을 제외하고 번들 및 라이선스 고지를 유지합니다. Electron 런타임 전체 크기나 유휴 RAM 개선율을 뜻하지 않습니다.
