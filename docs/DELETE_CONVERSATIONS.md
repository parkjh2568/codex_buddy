# 이전 대화 삭제

`이전 대화` 항목 오른쪽 `···`의 `대화 삭제`를 선택합니다. 삭제 창에서 대화 제목과 범위를 확인한 뒤 `영구 삭제`를 눌러 실행합니다. 기본 포커스는 `취소`이며 Esc로 취소할 수 있습니다. 삭제 처리 중에는 버튼과 Esc 취소를 막아 완료 여부를 명확하게 표시합니다.

## 삭제 범위

옹기봇에 등록된 대화 ID만 처리합니다. 로컬 목록 인덱스와 `conversations/<ID>.json`, 해당 대화의 `.tmp`를 제거합니다. 현재 대화를 삭제하면 현재 메시지·thread 연결·입력 초안 캐시도 정리해 새 대화 상태로 돌아갑니다. 다른 대화와 모델/추론/속도 설정은 유지합니다.

CLI 세션 ID가 있으면 저장된 CLI 연결의 `thread/delete`를 사용합니다. 정상 삭제는 CLI의 실제 rollout 파일과 관련 메타데이터를 제거하며 파생된 하위 세션도 함께 처리합니다. 삭제 알림에서 확인된 다른 옹기봇 소유 ID가 있으면 그 로컬 기록도 정리합니다. 연결된 CLI 세션이 없는 체험/로컬 대화는 로컬 기록만 제거합니다. [공식 OpenAI App Server 문서](https://learn.chatgpt.com/docs/app-server)

앱에서 되돌리기를 제공하지 않습니다. 기존 이관/손상 복구용 `state.json.backup-*` 등의 백업과 외부 백업은 별도로 유지하며 이번 삭제 대상에 포함하지 않습니다. 삭제 창에도 이 범위를 표시합니다. 디스크의 보안 삭제나 모든 외부 사본 제거를 보장하는 기능은 아닙니다.

실행/대기/접수/기록 조회 중에는 삭제할 수 없습니다. 외부 Codex 세션 ID를 입력해 임의 삭제할 수 없고, 삭제 확인이 없는 IPC 요청도 거절합니다. 같은 세션이 다른 CLI에서 실행 중이면 CLI가 삭제를 거절할 수 있으며 앱에 해당 오류를 표시합니다.

## 순서와 실패 처리

1. 현재 기록을 저장하고 `delete-journal.json`에 대상 소유 ID와 CLI 연결 정보를 기록합니다. 본문 복사본은 넣지 않습니다.
2. CLI 세션이 있으면 같은 CLI/작업 폴더의 소유 대화를 조회해 파생 관계를 확인하고 삭제 범위를 저널에 고정합니다. 관계 조회는 최대 4개씩 동시에 수행하며 하나라도 불확실하면 진행 중인 조회가 끝난 뒤 실패를 반환하고 실제 삭제를 요청하지 않습니다. 다른 CLI/작업 폴더에 연결된 대화는 별도 프로세스를 사용해 현재 대화 연결을 유지합니다.
3. 실제 세션 삭제를 요청하고 파생 세션의 부재까지 확인한 뒤 저널을 `cli-deleted`로 확정하고 목록 인덱스에서 대상 ID를 제거합니다.
4. 해당 JSON과 임시 파일을 제거하고 삭제 저널을 지웁니다.

CLI 오류/연결 중단/확인되지 않은 응답에서는 로컬 기록을 유지합니다. 해당 항목에 `삭제 확인 필요`를 표시하고 `···`의 `대화 삭제 재시도`로 다시 확인할 수 있으며, 삭제 확인이 필요한 대화의 재개/새 질문은 막습니다. 다른 대화와 새 대화는 사용할 수 있습니다. 여러 삭제를 동시에 진행하지 않습니다.

관계 조회·삭제·부재 확인 RPC는 같은 30초 deadline의 남은 시간을 사용합니다. 이 예산은 시스템 시각 조정에 영향받지 않는 경과 시간으로 계산합니다. 연결이나 관계 조회가 끝났을 때 예산이 소진됐으면 새 삭제 RPC를 보내지 않습니다. 이미 성공한 삭제 응답의 로컬 확정은 시간 초과로 중간에 끊지 않습니다. 동시 조회는 지연을 줄이는 처리이며 소유 대화 수만큼의 read RPC 자체를 줄이지 않습니다. timeout·종료·ID 불일치·관계 확인 실패를 삭제 성공으로 처리하지 않습니다. 원격 삭제가 이미 성공한 뒤 파생 세션 확인이 실패한 경우에도 로컬 기록과 저널을 보존해 재확인합니다.

전체 버튼 처리 시간이 반드시 30초 이내라는 의미는 아닙니다. 접수 전 진행 중인 저장 대기, 동기 파일 처리와 이미 공유 중인 CLI 연결의 초기화 대기는 별도입니다. 연결 API의 초기화 제한은 기존 30초이며 삭제 요청의 남은 예산을 전달하지 않습니다. 연결을 포함한 엄격한 제한은 공유 연결을 다른 작업에서 끊지 않는 계약을 먼저 설계해야 합니다.

CLI 삭제 후 로컬 파일 정리가 실패하면 부분 완료를 알리고 저널을 보존합니다. 같은 확인 창에서 다시 시도하거나 앱을 재시작하면 확인된 로컬 정리를 마무리합니다. CLI 확인 전의 pending 삭제는 재시작해도 자동으로 원격 삭제하지 않으며 사용자가 다시 확인합니다. 확인값/소유/경로가 맞지 않으면 파일을 지우지 않습니다.

기존 설치 CLI 0.160.0 검증에서는 이미 없어진 세션의 반복 삭제에 `-32600`, `no rollout found for thread id <ID>`를 반환했습니다. 이 정확한 오류와 동일 ID의 재조회 부재를 함께 확인한 경우에만 로컬 정리를 계속합니다. 인증/네트워크/미지원 메서드 오류를 이미 삭제된 세션으로 취급하지 않습니다. 향후 CLI에서 오류 방식이 달라지면 보존 후 오류 표시가 우선입니다.

삭제 완료 알림은 RPC 응답 뒤 도착할 수 있습니다. 앱은 알림 하나의 즉시 도착에만 의존하지 않으며 요청 성공을 기준으로 대상 루트를 처리합니다.

## 검증

단위·삭제 화면·실제 CLI 삭제 검사의 실행 조건과 명령은 [검증 가이드](BUILD_GUIDE.md#4-검증-명령과-현재-windows-한계)를 따른다. 실제 CLI 검사는 별도로 만든 소유 세션만 사용하며 계정 이용량을 사용한다. 최신 후보의 실행 검증 상태는 [릴리스 현황](ALPHA_REPORT.md), 삭제 회귀와 모의 RPC 지연 측정은 [구현 결과](history/IMPLEMENTATION_RESULT_2026-10-19.md)에 있다. 모의 지연 감소를 실제 CLI/network 속도 개선으로 해석하지 않는다.

## 삭제 소유 범위

같은 threadId라도 다른 CLI 실행 파일·작업 폴더의 로컬 대화는 삭제 대상에 추가하지 않습니다. 원격 삭제 전에 beginDeletion으로 소유 범위를 기록하고, Store.completeDeletion도 그 ID 범위의 부분집합만 받습니다. cli-deleted 단계의 재시작은 목록 제거 뒤 남은 파일 정리를 허용합니다. 인증·전송 실패를 세션 부재로 취급하지 않습니다. 현재 회귀와 검증 CLI 버전은 [수정 결과](history/ISSUE_REMEDIATION_RESULT_2026-10-08.md)를 참고합니다. 당시 28개·CLI 0.160.0 결과는 [검증 이력](history/MEASUREMENTS_BEFORE_CLEANUP_2026-10-10.md)에 보존한다.
